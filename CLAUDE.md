# Git — Atualização Automática

Após concluir qualquer conjunto de mudanças neste projeto, **sempre** faça commit e push para o repositório remoto:

```
git add <arquivos modificados>
git commit -m "<mensagem descritiva>"
git push origin main
```

- Use mensagens de commit em português, descritivas do que foi feito
- Adicione apenas os arquivos modificados (nunca `git add -A` sem revisar)
- Nunca force-push em `main`
- Sempre faça push ao final de cada tarefa concluída

# Versão do Sistema

A versão fica em `src/lib/version.ts` (constante `APP_VERSION`) e exibida no rodapé do sidebar.

**Regra:** a cada conjunto de mudanças commitado, incremente a versão seguindo semver:
- `patch` (x.x.**N**) — correções de bugs, ajustes visuais, pequenas melhorias
- `minor` (x.**N**.0) — funcionalidades novas ou mudanças relevantes de UX
- `major` (**N**.0.0) — mudanças arquiteturais grandes (raramente)

Atualize `src/lib/version.ts` junto com os demais arquivos no mesmo commit.

Plataforma de ensino para agentes de viagem. Next.js App Router + Supabase.

## Stack
- **Frontend**: Next.js App Router, TypeScript, Tailwind CSS, shadcn/ui, Lucide icons, Sonner (toasts)
- **Backend**: Supabase (Postgres + Storage + Auth)
- **Tabelas principais**: `profiles`, `training_items`, `training_materials`, `notifications`, `announcements`, `site_settings`, `lessons`, `modules`, `courses`

## Supabase
- `createClient()` — cliente com sessão do usuário (respeita RLS)
- `createAdminClient()` — usa `SUPABASE_SERVICE_ROLE_KEY`, bypassa RLS; use para operações admin
- Projeto ID: definido em `NEXT_PUBLIC_SUPABASE_URL` (ver `.env.local`)
- RLS `profiles`: usuário lê/edita apenas o próprio; admins leem todos (`profiles_select_admin`)
- Notificações: INSERT via `adminClient` (sem política de INSERT — service role bypassa RLS)
- **Relações N→1** (ex.: `tags(name)`, `courses(name)`, `lessons(title)` em joins): o PostgREST retorna **objeto** em runtime, mas o client sem tipos gerados infere **array**. Nunca acesse com `.map()`/`[0]` direto — use `toOne()` de `src/lib/supabase/relations.ts`, que normaliza as duas formas. (Regressão real na v1.50.1: Marketing quebrou com `t.tags.map is not a function` só para usuários com tags.)
- Triggers em `profiles` disparados via auth (GoTrue) rodam com `search_path` restrito — sempre qualifique objetos com `public.` dentro de funções de trigger (ver migração 030).
- **RLS bloqueia joins embutidos para linhas de outro dono, silenciosamente** (sem erro, só vem `null`/vazio): se a query do MEMBRO (client de sessão) faz embed tipo `profiles!fk(full_name)` para um `id` que não é o dele mesmo (ex.: nome do admin responsável por um chamado), a RLS de `profiles` (só lê o próprio perfil) barra o join e o campo volta vazio — mesmo a linha principal sendo do próprio membro. Real em `getMyFeedbackReports` (`src/app/actions/feedback.ts`): resolvido trocando para `adminClient` com filtro explícito `.eq('user_id', user.id)` (a checagem de posse fica no filtro, não na RLS).
- Pacotes `@tiptap/*` precisam ficar todos na MESMA versão exata (ver `package.json`) — as extensões fixam peer dependency `@tiptap/core` na versão exata, não em range; um caret (`^`) num único pacote causa conflito de peer dependency no `npm install` assim que o tiptap publica um patch novo.
- `<Select>` (`src/components/ui/select.tsx`) é baseado em `@base-ui/react/select`, não Radix. **`<SelectValue />` sozinho renderiza o valor bruto**, não o label do `<SelectItem>` selecionado — ele não escaneia os itens renderizados. Precisa de `<SelectValue>{(v) => label[v]}</SelectValue>` (função de mapeamento) ou do prop `items` no `<Select>` raiz. Sem isso, o trigger mostra o `value` cru (ex.: um UUID) em vez do texto — bug real visto no seletor de "Responsável" em `feedback-panel.tsx`.
- **`toast()` (sonner) chamado no primeiro `useEffect` de montagem de uma página pode ser perdido silenciosamente.** O `<Toaster/>` (root layout) só recebe eventos publicados DEPOIS que seu próprio efeito de `ToastState.subscribe()` rodar — e esse subscribe não faz replay de toasts anteriores. Como `{children}` vem antes de `<Toaster/>` no JSX do `src/app/layout.tsx`, um `toast()` disparado no efeito de mount de uma página corre — e às vezes perde — a corrida contra o subscribe do Toaster (mesmo commit, ordem de efeitos por posição na árvore). Sintoma: nenhum erro, o toast simplesmente não aparece, um clique/ação do usuário depois disparando outro toast funciona normal (não é o Toaster que está quebrado, só a chamada síncrona no mount). Correção: empurrar a chamada com `setTimeout(() => toast(...), 0)`. Caso real: toast de "desconectado por inatividade" em `src/components/auth/login-form.tsx` após redirect de `idle-logout-guard.tsx`.

## Papéis e autorização (admin / collaborator / member)
- `profiles.role` aceita `'admin' | 'member' | 'collaborator'` (migração `036`). **Colaborador** = pessoa interna que cria/edita conteúdo apenas da sua área, e estuda como membro comum no `/dashboard` (sem preview de rascunho).
- **Áreas de colaborador** são configuráveis pelo admin (tabela `collaborator_areas`: `name` + `capabilities text[]`), geridas em Admin → Membros → "Áreas de Colaborador" (`collaborator-areas-manager.tsx`). Cada colaborador pertence a UMA área (`profiles.collaborator_area_id`). **Decisão: NÃO reutilizar `tags`** — tags têm semântica de visibilidade de aluno; misturar criaria risco de apagar uma "tag-área" sem perceber que dava poder de escrita.
- **Capacidades** (enum fixo em `src/lib/capabilities.ts`): `courses` (cursos+módulos+aulas), `trainings`, `marketing`, `comercial`, `aereo`, `famtours`, `grupos`. Premiação (TamoJunto Winners), PodViajar e Corrida de Vendas gravam settings globais (`site_settings`, sem `owner_area_id` — não fazem sentido "por posse"), mas são editáveis por quem tem a capacidade `marketing` via `requireCapability('marketing')` + prop `canEdit`. Quando `!canEdit`, mostrar banner âmbar explicando o motivo, não só desabilitar os controles.
- **Cor de tag é hex livre** (`tags.color` aceita `#rrggbb` ou as 10 chaves antigas). Ao renderizar cor de tag em lugar novo, usar `getTagColor()` de `src/lib/tag-colors.ts` e aplicar via `style` inline — **não** `className` (hex arbitrário em runtime não vira classe Tailwind).
- **Dono do conteúdo**: `owner_area_id` (nullable, NULL = global/admin) em `courses`, `training_items`, `marketing_items`, `famtours`, `grupos`, `commercial_conditions`. `modules`/`lessons` herdam via `course_id`. **Reorder global (cursos/módulos/treinamentos) é admin-only** — reordenar um subconjunto bagunçaria os índices; reorder de aulas (escopado ao módulo) exige posse do curso pai.
- **Bug real corrigido (v1.112.5, chamado CLV-0031): o escopo de colaborador em Relatórios → Atividades só cobria `curso`/`módulo`/`aula`**, mesmo depois de `owner_area_id` ter se espalhado para `famtours`/`training_items`/`marketing_items`/`grupos`/`commercial_conditions` (item acima). Pra uma área sem curso nenhum (ex.: "Marketing", que trabalha com treinamento/item de marketing/famtour), o filtro de posse (`atividades-log.tsx`) sempre caía no fallback `id = 00000000...` — a aba ficava **permanentemente vazia, com ou sem filtro nenhum aplicado**. O usuário reportou como "os filtros não funcionam" (testou usuário/período/tipo/ação, nada retornava), mas a causa era a query de base, não qualquer filtro específico. Corrigido estendendo o escopo (`scopeToOwnCourses` em `relatorios/page.tsx` + `AtividadesScope` em `atividades-log.tsx`) para também considerar `famtour`/`treinamento`/`item_marketing`/`grupo`/`condicao_comercial` (via `owner_area_id` nas respectivas tabelas), e o dropdown "Tipo de conteúdo" a listar essas opções pro colaborador (antes só oferecia Curso/Módulo/Aula, mesmo pra quem nunca mexe nisso). **Ao estender `owner_area_id` pra uma tabela nova, sempre conferir se o escopo de Atividades (ou qualquer outro filtro "de posse") também precisa ser atualizado** — os dois lugares evoluíram de forma independente antes desse fix.
- **Colaborador VÊ TUDO, só EDITA o que tem capacidade + posse** (v1.71.0 — antes era "só vê o que é seu"). `/admin/cursos` e `/admin/marketing` (as duas únicas telas de conteúdo) mostram TODOS os cursos/treinamentos/itens/famtours/grupos/condições de TODAS as áreas pra qualquer colaborador, inclusive abas sem nenhuma capacidade relacionada (Comercial, Aéreo, Grupos, Corrida de Vendas, Premiação, PodViajar aparecem sempre, em modo leitura). Abrir o detalhe de um curso/módulo/aula de outra área **não bloqueia mais** — abre normal, só os controles de mutação ficam escondidos/desabilitados. Cada tela calcula `canEdit`/`canCreate` (`ctx.role === 'admin' || (ctx.capabilities.includes(cap) && item.owner_area_id === ctx.areaId)`) e repassa como prop pros componentes — **isso é só UX**, a segurança real continua 100% nos guards de mutação (item abaixo), que não mudaram. Padrão de UI pro modo leitura: `<fieldset disabled={!canEdit}>` em volta de formulários inteiros (desabilita inputs/botões nativamente em cascata) + condicionais explícitas pra overlays de upload e pro toolbar do `RichTextEditor` (prop `editable`, não é controle de formulário nativo, fieldset não alcança). Em listas de item (famtours/grupos/etc, fora de um único form), cada botão de Editar/Excluir/Publicar fica atrás de `{item.canEdit && (...)}` explícito — o link de ABRIR o detalhe fica sempre visível (é a porta de entrada pro modo leitura).

Ao criar action nova, sempre incluir guard — o gate do layout não protege actions.

- `notifyAllMembers` e o `notifyMembers` de training incluem `role IN ('member','collaborator')` — colaboradores também estudam e recebem avisos.

Critério certo, já usado em `relatorios/page.tsx`: `role !== 'admin'` (ou `IN ('member','collaborator')`), nunca `= 'member'` isolado. **Mesma classe de bug encontrada de novo (v1.113.4)**: `notifyNewAnnouncement` (`src/app/actions/announcements.ts`) mandava o e-mail de comunicado (RD Station) só pra `role='member'` — a notificação in-app (`notifyAllMembers`, mesma função) já incluía colaborador corretamente, só o e-mail estava errado. Achado ao investigar por que colaboradores reais nunca recebiam o comunicado por e-mail (a query de audiência do lado da RD Station estava correta — o problema era que o evento nunca era disparado pra essas pessoas em primeiro lugar).
- **Atrás do proxy reverso da VPS, `request.url` / `request.nextUrl.origin` refletem o endereço INTERNO** (`http://localhost:3000/...`), não o domínio público — o nginx não repassa `Host`/`X-Forwarded-*`. Para montar URL absoluta num route handler, usar `process.env.NEXT_PUBLIC_SITE_URL ?? 'https://universidadelv.com.br'`. O `.env.local` precisa de `NEXT_PUBLIC_SITE_URL=http://localhost:3000`, senão o dev local redireciona para produção. **Bug real confirmado em produção (v1.113.1)**: `src/app/auth/callback/route.ts` usava `const { origin } = new URL(request.url)` pra montar o redirect final — em produção isso mandava o usuário pra `https://localhost:3000/reset-password` (inacessível pro navegador dele) em vez do domínio real, quebrando o fluxo de redefinição de senha logo após o Supabase confirmar o link corretamente. Corrigido trocando por `process.env.NEXT_PUBLIC_SITE_URL ?? 'https://universidadelv.com.br'`, mesmo padrão já usado em outros lugares do projeto — **qualquer route handler novo que precise montar uma URL absoluta de redirect deve seguir esse padrão desde o início**, nunca `new URL(request.url).origin`.
- **Detalhes em [docs/historico-tecnico.md](docs/historico-tecnico.md#papéis-e-autorização-detalhes-e-histórico)**: menu do colaborador item a item, fluxo de cadastro pendente (aprovar/recusar/reconsiderar), modo prévia "ver como colaborador" (`getPreviewAreaContext`, cookie, route handler GET), e os bugs de redirect de feedback já corrigidos.
- **`proxy.ts` roda em toda rota que não seja `_next/static`/`_next/image`/favicon/imagem** (ver `config.matcher`) — isso inclui as rotas especiais de metadata do Next (`src/app/sitemap.ts` → `/sitemap.xml`, `src/app/robots.ts` → `/robots.txt`). Bug real corrigido (v1.99.1): essas duas não estavam na lista `isPublic`, então qualquer visitante sem sessão (inclusive o Googlebot) recebia um redirect 307 pro `/login` em vez do conteúdo — o Google nunca conseguia de fato ler o sitemap/robots do site. Ao adicionar uma rota de metadata nova (`opengraph-image`, `manifest.ts`, etc.), sempre incluir em `isPublic`.
- **Segundo bug real, mesmo botão, causa totalmente diferente (v1.99.2)**: os links "Ver sitemap.xml"/"Ver robots.txt" em Admin → Configurações → SEO (`seo-manager.tsx`) montavam a URL como `` `${seoCanonicalUrl || '#'}/sitemap.xml` `` — com `seo_canonical_url` vazio no banco (o campo mostrava só o `placeholder` cinza, não um valor salvo), o link virava `#/sitemap.xml`, uma âncora relativa à própria página (`/admin/seo#/sitemap.xml`), nunca navegando pra lugar nenhum. Corrigido usando link relativo fixo (`href="/sitemap.xml"`) em vez de depender da URL canônica — resolve contra a origem atual sempre, funciona local e em produção, e não quebra mais se o campo estiver vazio. **Ao montar link/URL a partir de um `site_settings` de texto livre, sempre considerar que o campo pode estar vazio** (o valor exibido no input pode ser só o placeholder).
- **Terceiro bug real no `robots.txt`, achado ao revisar o conteúdo gerado (v1.99.3)**: `disallow: [..., '/print/']` em `src/app/robots.ts` mirava um caminho que nunca existiu — a página de certificado fica em `src/app/(print)/certificado/[id]/page.tsx`, mas `(print)` é *route group* do App Router (parênteses = organização de pasta, não entra na URL). A URL real é `/certificado/[id]`, então a regra nunca bloqueava nada. Corrigido pra `Disallow: /certificado/` (essa página é pessoal/por-membro, não faz sentido indexar — bate com a página já ficar atrás de login no `proxy.ts`, que não a lista em `isPublic`). **Ao escrever regra de robots/sitemap que referencia uma rota, sempre conferir a URL real gerada pelo App Router, não o caminho da pasta** — route groups `(nome)` e pastas dinâmicas `[id]` mudam a URL final de formas não óbvias.

Sem aba nova.

Reenvio depois de negado é um `upsert` que reseta `status='pending'` na MESMA linha, não uma linha nova — sem histórico de N tentativas na tabela (o histórico de verdade fica em `admin_activity_log` via `logActivity`, mesmo padrão de outras partes do projeto que preferem "estado atual na tabela + auditoria separada" a duplicar histórico em dois lugares). - **Bug real (PGRST201) encontrado testando**: a query em `admin/marketing/page.tsx` que busca solicitações pendentes em bulk (`training_access_requests.select('..., profiles(...)')`) voltava **vazia, sem exception nenhuma no client** — o Supabase-js engole o erro de embed ambíguo e só retorna `data: null`. Causa: `training_access_requests` tem **duas** FKs pra `profiles` (`member_id` e `resolved_by`) — o PostgREST recusa (`PGRST201`, "more than one relationship was found") inferir sozinho qual usar. Corrigido qualificando explicitamente: `profiles!training_access_requests_member_id_fkey(...)`. **Sempre que uma tabela tiver 2+ FKs pra outra tabela, todo embed do PostgREST precisa nomear a constraint** — sem isso o sintoma é dado sumindo em silêncio (contador de pendentes sempre zerado), não um erro visível.
- **`isTrainingLocked(item, myUf, requestStatus)`** (`src/lib/training-access.ts`, puro, sem `'use server'`) centraliza a decisão: UF batendo OU pedido aprovado destrava; `exclusive_ufs` vazio nunca bloqueia. Chamado nos 3 pontos de exibição (`dashboard/treinamentos/page.tsx`, `.../[id]/page.tsx`, widget da home) a partir de `getMyTrainingAccessContext()` (`src/app/actions/training-access.ts`) — evita duplicar a lógica em cada Server Component.

Um treinamento "exclusivo" que vazasse o vídeo/link/material pra quem não tem acesso tornaria o bloqueio decorativo.

(sem botão) — o botão completo de solicitar mora na página de detalhe, pra onde o card já leva ao clicar. Só `HappeningNowBanner`/`FeaturedLiveCard` (já tinham CTA proeminente e espaço) e a própria página de detalhe mostram o botão inteiro na lista. **Decisão confirmada com o usuário**: o widget compacto da home (`SidebarTrainingCard`) usa só o selo, do mesmo jeito.

## Anexos de chamado (foto e documento)

- `feedback_attachments` guarda **os dois casos** (migração `049`): `event_id NULL` = anexo da abertura do chamado; `event_id` preenchido = anexo daquela resposta (`feedback_events`). `mapReports` filtra por isso — sem o filtro, o anexo da resposta apareceria duplicado no topo do chamado.
- **Dois uploads distintos, de propósito**: `uploadFeedbackFile` (só imagem, vira `<img>` inline no editor) e `uploadFeedbackAttachment` (imagem **ou** PDF/Word/Excel/texto, vira anexo listado). O segundo valida contra `ALLOWED_ATTACHMENT_MIME`; `toWebP()` devolve o arquivo intacto quando não é imagem, então dá pra chamar sempre.
- **Render**: imagem continua com thumbnail + `ImageLightbox`; documento usa `AttachmentFileChip` (`src/components/ui/attachment-file-chip.tsx`). Ao montar o índice do lightbox, indexar **só as imagens** — misturar documento na contagem abre a imagem errada.
- `NoteAttachmentPicker` (`src/components/ui/note-attachment-picker.tsx`) é o picker de resposta, compartilhado entre admin e membro (a `addFeedbackNote` é bidirecional). Recebe `idSuffix` porque vários cards ficam abertos ao mesmo tempo e o `<input type="file">` precisa de id único.
- A restrição real de tipo é do **bucket** (`allowed_mime_types`), não só do código — confirmado que rejeita executável, zip e HTML mesmo via service role. Ao liberar um tipo novo, mexer nos dois lugares.
- **Nunca validar anexo só por `file.type`** — o navegador não é confiável. Um `.docx`/`.doc` vindo de Windows sem a associação de tipo registrada chega como `application/octet-stream`, e era rejeitado tanto pela action quanto pelo bucket (bug real da v1.89.1: "não dá pra anexar Word"). `resolveAttachmentMime()` aceita o MIME quando reconhecido e **cai na extensão** quando não; o arquivo é reembrulhado com o tipo resolvido antes de subir, senão `toWebP()` não reconhece imagem e o bucket recusa.
- Como a extensão passou a valer, **a extensão salva vem do MIME resolvido, nunca do nome original** (`extForMime`/`safeFileName`): um `x.exe` enviado com MIME de PDF forjado seria gravado como `.exe` e baixado como executável pelo outro lado do chamado. Vira `x.pdf` no storage e no nome exibido.
- **Bug real corrigido (v1.112.6, chamado CLV-0034): anexar um vídeo (ou qualquer arquivo grande) em `uploadFeedbackAttachment` ficava "tentando enviar" por minutos, sem erro.** O `accept="image/*,.pdf,..."` do `<input type="file">` é só filtro de UI — dá pra escolher "Todos os arquivos" no seletor do SO — e nem `feedback-ticket-form.tsx` nem `NoteAttachmentPicker` tinham guard de tamanho no cliente nem `try/catch` em volta da chamada da action, mesma classe de bug já documentada e corrigida em `corrida-vendas-manager.tsx`/`famtours-manager.tsx`/`trainings-manager.tsx`: um arquivo grande (vídeo facilmente >10MB) estoura o `bodySizeLimit` do Next (`next.config.ts`) **antes** da validação de tipo do servidor rodar, e sem o guard o usuário só via o upload girando até desistir. Corrigido replicando as duas camadas (guard de 8MB com toast explícito + `try/catch`) nos dois pontos de entrada — `handleAttachmentPick` (abertura do chamado) e `handlePick` (`NoteAttachmentPicker`, resposta, compartilhado entre admin e membro).

## `RichTextEditor`: rascunho em sessionStorage + toolbar sticky (v1.97.0)

- **Rascunho** (abertura de chamado + resposta admin/membro): `src/lib/session-draft.ts` (`readDraft`/`writeDraft`/`clearDraft`) usa **sessionStorage**, não localStorage — esses componentes não têm o id do usuário disponível no cliente pra escopar a chave, e localStorage persistiria indefinidamente; num navegador compartilhado entre contas diferentes um rascunho vazaria pro próximo login. sessionStorage soma "sobrevive a reload" com "some sozinho ao fechar a aba", sem precisar de prop nova. Escrita é síncrona a cada mudança (sem debounce) — é storage local, não chamada de rede, então não tem custo de disparar por tecla.
- **Bug real corrigido no caminho**: `RichTextEditor` só lê a prop `content` **na montagem** — mudar o state depois (ex.: ao restaurar um rascunho num `useEffect`) não atualiza o editor já montado, o texto fica "preso" no state sem aparecer na tela. Mesmo motivo por trás do padrão `noteResetKey`/`replyResetKey` que já existia em `feedback-panel.tsx`/`my-feedback-list.tsx` (bump de um contador usado como `key` força remontagem). Ao restaurar um rascunho, é preciso bumpar essa key **junto** com o `setState` do conteúdo restaurado (mesmo `useEffect`, mesmo commit) — só ajustar o state não é suficiente, e só bumpar a key sem o novo state ainda montaria vazio.
- **Mesmo bug de `overflow-hidden` também no CARD que envolve o editor (v1.97.1)**: corrigir só o wrapper interno do `RichTextEditor` não bastou — o **card do próprio chamado** (`feedback-panel.tsx`/`my-feedback-list.tsx`, e o card de cada corrida em `corrida-vendas-manager.tsx`) também tinha `overflow-hidden rounded-xl` envolvendo a resposta, e é ele quem vira a âncora de rolagem primeiro (mais próximo do editor que a página). Testar sticky **só na tela de abrir chamado novo** (sem card ao redor) não pega esse caso — o teste inicial passou porque testou o lugar errado. Mesma correção: tira o `overflow-hidden` do card, bota `rounded-t-xl`/`rounded-xl` (conforme aberto/fechado) só no botão de cabeçalho, que é o único filho com fundo próprio tocando a borda. **Ao usar `overflow-hidden` só pra arredondar canto, sempre perguntar se há um sticky (ou vai haver) em algum descendente.**
- **Bug real corrigido, CSS**: o wrapper externo do editor tinha `overflow-hidden` (pro conteúdo respeitar o `rounded-lg` do card) — mas `overflow` diferente de `visible` num ancestral, mesmo sem barra de rolagem própria, vira a "âncora de rolagem" de qualquer `position: sticky` lá dentro. Como esse wrapper nunca rola de verdade (quem rola é a página atrás dele), o toolbar sticky nunca "grudava". Corrigido tirando o `overflow-hidden` do wrapper e movendo o arredondamento pros dois filhos (`rounded-t-lg` no toolbar, `rounded-b-lg overflow-hidden` no `EditorContent`) — sticky volta a funcionar porque agora sobra a página (ou o modal/dialog em volta) como ancestral de rolagem real. **Ao adicionar sticky dentro de um card com cantos arredondados, nunca colocar `overflow-hidden` num ancestral direto do elemento sticky.**

## Colar HTML bruto no `RichTextEditor` sem filtro reproduzia outro editor inteiro dentro do texto

- **Bug real corrigido (v1.96.1)**: selecionar um trecho da própria página que abrangesse a barra de ferramentas + área de outro `RichTextEditor` aberto ao lado (ex.: responder um chamado com outra resposta rica visível na tela) e colar (Ctrl+V) em um editor diferente inseria a estrutura bruta — `<div>`/`<button>`/`<svg>` com as MESMAS classes Tailwind do toolbar real — como se fosse conteúdo. Causa: sem sanitização, o Tiptap tenta honrar a estrutura HTML do clipboard tal como veio.
- Corrigido com `transformPastedHTML` (`sanitizePastedHtml()` em `src/components/ui/rich-text-editor.tsx`) — roda ANTES do ProseMirror parsear o HTML colado: qualquer tag fora de uma lista fixa (`p`, `br`, `strong`, `em`, `u`, `h2`, `h3`, `ul`/`ol`/`li`, `blockquote`, `a`, `img`) é desembrulhada (o texto de dentro sobe, a tag some) em vez de inserida — isso já elimina `button`/`svg`/`div` com qualquer classe, sem precisar de allowlist de atributo por atributo. Tags permitidas só mantêm `href`/`src`/`alt`, descartando `class`/`style`/`contenteditable` de qualquer origem. Colar formatação legítima (negrito, lista, link de um site normal) continua funcionando — só a estrutura "de aplicativo" (toolbar/botão/svg) é que se perde.

## Card clicável do Dashboard ("Aguardando Correção") parecia não responder no celular — não era bug de área de clique

- **Se esse padrão de "parece travado" aparecer em outro link/card clicável do painel admin**: mesma causa provável (navegação real de Server Component demorando sem feedback, não bug de hit-area) — antes de mexer em CSS/z-index, cronometrar com `waitForURL` como foi feito aqui.

## Notificação push nativa do navegador/SO (Web Push, v1.119.0)

- **Opt-in por navegador/dispositivo, não por conta** — cada combinação usuário+navegador precisa autorizar uma vez (o popup nativo do navegador). Aceitar no Chrome do notebook não cobre o celular; a pessoa vê o prompt de novo lá. Não dá pra ligar isso silenciosamente para todo mundo — é limitação do próprio Web Push, não do código.
- **Complementa a notificação do sino, não substitui** — toda chamada que já insere em `notifications` (`notifyUser`/`notifyAllMembers`/`notifyCourseMembers`/`notifyAllAdmins`/`notifyCourseOwners`, todas em `src/app/actions/notifications.ts`) agora também chama `sendPushToUsers()` (`src/lib/webpush.ts`), fire-and-forget, logo após o insert — os dois canais recebem exatamente o mesmo conjunto de eventos, sem lista própria de "quais tipos merecem push" (decisão do usuário: todas as notificações, não só as urgentes).
- **`push_subscriptions`** (migração `060`): uma linha por navegador/dispositivo inscrito (`endpoint` é a chave natural, único). Sem RLS de leitura — mesmo padrão de `rdstation_tokens`/`short_links`: o insert/delete do próprio usuário passa por server action com guard (`src/app/actions/push-subscriptions.ts`, `subscribeToPush`/`unsubscribeFromPush`), não por policy.
- **Endpoint expirado/revogado (404/410 do serviço de push) limpa a própria linha sozinho** — `sendPushToUsers()` detecta esses dois status e apaga a subscription; qualquer outro erro (rede, etc.) só loga, não apaga (pode ser transitório).
- **UI de ativação mora dentro do próprio `NotificationBell`** (`src/components/members/notification-bell.tsx`) — um banner "Ative para receber avisos mesmo com a aba fechada" aparece no topo do painel só quando faz sentido oferecer (`Notification.permission` ainda não decidida e sem subscription salva); nunca aparece se o navegador não suporta, ou se a pessoa já negou antes (não dá pra reabrir esse prompt programaticamente, só a própria pessoa mudando nas configurações do navegador). Compartilhado pelas 3 sidebars (membro/colaborador/admin) de graça, já que é o mesmo componente.
- **`public/sw.js`**: service worker mínimo, só escuta `push` (mostra a notificação) e `notificationclick` (foca aba existente com a URL ou abre uma nova) — sem cache/offline de propósito, não é isso que resolve aqui.
- **Bug real corrigido no caminho**: `webpush.setVapidDetails()` exige um "subject" `https:` ou `mailto:` — a primeira versão usava `NEXT_PUBLIC_SITE_URL`, que em dev é `http://localhost:3000`, e isso quebrava a carga do módulo com exceção síncrona, derrubando **toda** Server Action que importa `notifications.ts` em cascata (ou seja, quase todas — login incluso) com "This page couldn't load". Trocado para `mailto:${ADMIN_EMAIL}`, que é válido em qualquer ambiente. **Qualquer env var usada como VAPID subject nunca pode ser a URL do site puro — sempre `mailto:` de um e-mail real.**
- **Chromium headless (Playwright) força `Notification.permission = 'denied'` por padrão** — bom pra confirmar que o banner fica escondido nesse estado (comportamento correto), mas não dá pra testar o fluxo real de "aceitar o prompt e receber notificação de verdade" por automação; isso só um navegador de verdade confirma (mesma classe de limitação já documentada pro Cloudflare Turnstile).
- **Pré-requisito de infraestrutura**: `NEXT_PUBLIC_VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY` no `.env.local` (gerar com `npx web-push generate-vapid-keys`, uma vez só, nunca trocar depois — trocar invalida todas as inscrições já feitas) e rodar a migração `060` no Supabase antes de funcionar em produção.
- **Bug real corrigido (v1.120.1)**: qualquer erro ao clicar "Ativar" (não só permissão negada) travava o banner escondido pra sempre, sem nenhum jeito de tentar de novo — reportado pelo usuário (colaborador Cesar) depois de um erro real ao ativar. Causa: `handleEnablePush` jogava `pushState` pra um estado terminal `'unavailable'` em qualquer `catch`, tratando "meu servidor rejeitou"/"rede falhou" igual a "o navegador bloqueou permanentemente". Corrigido separando os estados: só `Notification.permission === 'denied'` (o único caso onde o navegador de fato bloqueia reabrir o prompt via `requestPermission()`) trava num estado `'denied'` — que ganhou banner próprio com instrução (abrir o cadeado/info do site, liberar manualmente) + botão **"Já ativei, tentar de novo"** (só reconsulta `Notification.permission`, não tenta `requestPermission()` de novo — o navegador ignoraria mesmo). Qualquer outro erro volta pra `'offerable'`, deixando o botão "Ativar" disponível de novo. **Qualquer fluxo de permissão do navegador (push, geolocalização, câmera, etc.) precisa distinguir "negado de vez pelo usuário" de "falhou por outro motivo"** — só o primeiro justifica esconder a ação sem alternativa.

Corrigido pra `placement="header"` nos dois. **Ao adicionar um `NotificationBell` novo, o placement se decide pela posição visual do botão na tela (canto de sidebar vs. barra de topo), nunca por copiar o uso mais próximo no código.** De quebra, a largura fixa do painel (`320px`) ganhou um teto (`Math.min(320, window.innerWidth - 16)`) pra não estourar em celular bem estreito (<336px).
- **Segundo bug real no mesmo `placement="sidebar"` (v1.118.1, chamado CLV-0018): o painel cortava na borda direita da tela em retrato no menu mobile (drawer), mas ficava certo em paisagem.** O drawer mobile reaproveita o mesmo rodapé de sidebar (`SidebarContent` em `admin-sidebar.tsx`/`member-sidebar.tsx`), então o sino ali também usa `placement="sidebar"` — mas esse cálculo (`left: rect.right + 8`) nunca tinha um teto pra não passar da borda direita da viewport, diferente do branch `placement="header"` (que já tinha `Math.max(right, 8)`). No desktop nunca aparecia (sidebar estreita, tela larga, sempre sobra espaço à direita); no drawer mobile em retrato, o botão fica perto da borda esquerda de uma tela estreita (~390px) e o painel (320px) estourava pra fora. Em paisagem a viewport é larga o bastante pra caber mesmo sem o teto — por isso o bug era invisível nessa orientação, o que confundiu o diagnóstico inicial. Corrigido com `left: Math.min(rect.right + 8, window.innerWidth - panelW - 8)`, mesmo raciocínio de clamp que o branch `header` já usava. **Painel é portalado direto pro `document.body`** (`createPortal`), então não é um caso do bug de `overflow-hidden` cortando elemento posicionado (já visto em outros lugares do projeto) — o corte aqui era 100% da matemática de posicionamento em JS, sem CSS de ancestral envolvido.

## Indicador global de navegação (`NavigationProgress`, v1.117.0)

- **Problema relatado por usuários**: ao clicar num link pra ir pra outro lugar, a tela ficava "parada" sem nenhum sinal até a próxima página aparecer — mesma causa raiz já documentada no bug do card "Aguardando Correção" (navegação de Server Component sem feedback visual, não bug de área de clique), mas dessa vez pedido como solução **geral**, não um remendo por tela.
- **`src/components/navigation-progress.tsx`**, montado uma vez em `src/app/layout.tsx` (layout raiz — cobre login/admin/dashboard igual), sem props. Escuta clique em qualquer `<a>` interna (capture phase no `document`, sobrevive a `stopPropagation()` de qualquer componente no caminho) e reage à mudança de `usePathname()`/`useSearchParams()` pra saber quando a navegação terminou de verdade.
- **Decisão do usuário (2026-08-06): as duas fases combinadas**, não uma ou outra — barra fina no topo (`bg-primary`, 3px) aparece **imediatamente** no clique; se a navegação passar de 500ms, a barra some e entra um overlay de tela cheia (`bg-background/75 backdrop-blur`) com o `Spinner` (`src/components/ui/spinner.tsx`, já reaproveita `loading_image_url` de Configurações se o admin tiver customizado) + texto "Carregando...". Navegação rápida (<500ms) nunca mostra o overlay, só a barra concluindo rápido — evita "piscar" em telas já compiladas/rápidas.
- **Exclusões deliberadas do listener de clique**: `target≠_self` (abre em nova aba), `download`, `#`/`mailto:`/`tel:`, origem externa, e **`/api/*`** — essa última existe porque rota de API/download (ex.: `/api/relatorios/export`) não navega a página de verdade (é um download), então o pathname nunca muda e o indicador nunca seria escondido sem esse guard. Timeout de segurança de 15s força o reset se por algum motivo a navegação nunca completar (erro, etc.) — sem isso um caso não prevido deixaria o indicador travado pra sempre.
- **Não cobre navegação 100% programática** (`router.push()` fora de clique em `<a>`, ex.: redirect pós-login) — esses fluxos já tinham UI de pending própria antes disso existir (ex.: "Entrando..."/"Redirecionando..." do login) e continuam assim, sem conflito com o indicador global.
- **Testado com Playwright localmente** (não em produção — Turnstile bloqueia login automatizado, mesmo already-documented erro 600010): confirmado visualmente que a barra aparece no clique e que o overlay dispara quando a navegação é artificialmente atrasada além de 500ms (via `page.route()` interceptando a requisição). **Ao testar login automatizado localmente**, comentar temporariamente as 2 chaves do Turnstile no `.env.local` e reiniciar o dev server é a forma mais simples de contornar o bloqueio — sempre restaurar depois.

## Central de preferências de cookies na landing (v1.124.0, ajustada em v1.124.1)

- **`src/components/landing/cookie-consent.tsx`** substitui o antigo `cookie-banner.tsx` (deletado) — antes era só um banner "aceitar tudo", agora é um centro de preferências com 3 categorias (obrigatórios/estatísticas/marketing) + ícone flutuante persistente (canto inferior esquerdo) pra revisar a escolha depois, no mesmo padrão visual de outro produto do grupo (Litoral Verde). Só na landing pública (`src/app/page.tsx`), atrás do mesmo toggle `landing_lgpd_active` de sempre — texto/link continuam editáveis pelo admin (`landing_lgpd_text`/`_link_text`/`_link_url`; `_button_text` ficou sem uso depois da v1.124.1, ver abaixo); as 3 categorias e seus textos são fixos no código (boilerplate LGPD, não editável), decisão deliberada pra não criar campo de CMS pra isso.
- **Os toggles de "estatísticas"/"marketing" hoje só gravam a preferência** — o site não carrega nenhum script de analytics/marketing (sem GA/GTM/Meta Pixel) pra bloquear/liberar de verdade. `getCookiePrefs()` (exportado do mesmo arquivo) existe pra um script futuro checar antes de injetar a tag. Consentimento salvo em `localStorage['cookie_consent_v2']` (objeto JSON, não a chave antiga `cookie_consent` que era só uma string `'1'` — sem migração, aceitável pedir de novo uma vez no rollout).
- **v1.124.1 — sem faixa persistente, só ícone + dica temporária**: a v1.124.0 tinha uma faixa fixa no rodapé (banner "aceitar tudo"/"configurações") coexistindo com o ícone flutuante — usuário pediu pra tirar a faixa e deixar só o ícone, com uma "dica" saindo dele por ~3s na primeira visita (sem consentimento salvo) e sumindo sozinha (`HINT_DURATION_MS`, fade via classe condicional, sem lib de animação nova). A única forma de decidir as preferências agora é abrindo o modal pelo ícone — não existe mais atalho de "aceitar tudo" fora dele.
- **v1.124.3 — a correção da v1.124.1 (`body.style.overflow = 'hidden'` só durante o modal) não resolveu de verdade em celular real**, mesmo passando no teste automatizado da época. Causa: esse teste usava `page.mouse` (arraste de MOUSE) em Chromium headless, que não reproduz o gesto de PAN por toque de um navegador mobile de verdade — reconfirmado depois com toque real via CDP (`Input.dispatchTouchEvent`), que também não reproduziu no headless (limitação do próprio ambiente automatizado pra física de rubber-band/overscroll mobile, mesma classe de coisa que só se confirma num aparelho de verdade). A causa raiz real: o projeto nunca teve `overflow-x: hidden` como baseline em `html`/`body` — sem isso, QUALQUER overflow horizontal minúsculo (1px que seja, comum em landing page com elementos decorativos) já é suficiente pra habilitar o gesto de pan lateral em mobile, **independente** de travar o scroll via JS condicionalmente durante o modal (trava de scroll via JS não impede o pan de viewport baseado em layout mais largo que a tela — são mecanismos diferentes do navegador). Corrigido adicionando `overflow-x: hidden` global em `html`/`body` (`globals.css`, dentro do `@layer base`) — bloqueia até um `scrollTo()` forçado via JS, confirmado em teste. **Trava de scroll condicional via JS (só durante modal) não é o mesmo problema, nem substitui, uma baseline de `overflow-x: hidden` no documento inteiro** — a trava do modal continua útil (impede scroll VERTICAL de fundo enquanto o modal está aberto), mas não resolvia esse bug específico sozinha.
- **Bug real corrigido (v1.124.1): dava pra arrastar a tela lateralmente com o modal aberto, cortando o conteúdo torto** — o modal é construído do zero (`fixed inset-0`, não o `Dialog` compartilhado do projeto, pra ficar consistente com o resto da landing, que não usa `@/components/ui/*` em lugar nenhum), então não herdava o scroll-lock de fundo que uma lib de dialog acessível dá de graça. Sem isso, um `fixed` overlay não impede arrastar a página por baixo dele — e como a viewport visual em mobile é arrastável quando o documento tem qualquer overflow horizontal (mesmo 1px, comum em landing com elementos decorativos), o gesto de arrastar de lado "puxava" a tela inteira, modal incluso (que é fixed relativo à viewport, mas a própria viewport visual é que se move). Corrigido travando `document.body.style.overflow = 'hidden'` enquanto `view === 'modal'` (restaurado ao fechar). **Ao construir um modal customizado (sem usar `Dialog` do projeto), sempre replicar o scroll-lock de fundo manualmente — não é opcional, é o que impede exatamente esse tipo de bug.**
- **Achado de metodologia ao investigar um falso positivo no caminho**: um teste automatizado que tentava clicar no ícone flutuante travava, reportando outra seção da página "interceptando" o clique — parecia um bug real de z-index/positioning. Isolado com um diagnóstico direto (`getBoundingClientRect`/`elementFromPoint`/checagem de `transform`/`filter` em todos os ancestrais) que provou o ícone estava corretamente posicionado e clicável o tempo todo; a causa real era um seletor de texto do PRÓPRIO teste que não batia com o texto de verdade salvo no banco (`"cookies que usamos para melhorar"` vs. o `"cookies para melhorar"` assumido no teste), fazendo o Playwright ficar re-tentando/rolando a página como efeito colateral da busca falhando. **Antes de aceitar "elemento X intercepta o clique" como causa raiz, confirmar com `elementFromPoint` que não é o próprio teste com seletor errado.**

## Convenções
- Server actions ficam em `src/app/actions/`
- Componentes admin em `src/components/admin/`
- Componentes UI reutilizáveis em `src/components/ui/`
- `settings` são pares chave-valor na tabela `site_settings`; tipo e defaults em `src/lib/settings.ts`
- Nav do admin é duplicado em dois lugares que precisam ficar em sincronia: `NAV_ITEMS` em `src/components/admin/admin-sidebar.tsx` (render real, com ícone) e `ALL_NAV_ITEMS` em `src/components/admin/settings-form.tsx` (aba "Menu Admin", reordenável via `nav_order`). Ao adicionar página admin nova, adicionar nos dois + no default de `nav_order` em `src/lib/settings.ts`.
- **Perfil (admin e membro) é a MESMA tela**: `src/app/(admin)/admin/perfil/page.tsx` e `src/app/(members)/dashboard/perfil/page.tsx` renderizam o mesmo `<ProfileTabs>` (`src/components/members/profile-tabs.tsx`), cuja aba "Meu Perfil" usa `ProfileFormCompact` (`src/components/members/profile-form-compact.tsx`) — a pessoa edita o PRÓPRIO perfil aqui. Campos hoje: nome, email (read-only), avatar, empresa (`company`), cargo (`job_title`), LinkedIn (`linkedin_url`), salvos via `updateProfile` em `src/app/actions/profile.ts`. **`linkedin_url` também é editável pelo admin em nome de qualquer membro** (v1.102.0), via `EditMemberDialog` (`src/components/admin/edit-member-dialog.tsx`) → `updateMember` — os dois caminhos escrevem na mesma coluna, sem conflito.
- **`EditMemberDialog` é largo de propósito (`sm:max-w-2xl`, v1.102.0)** — o padrão de `DialogContent` é `sm:max-w-sm` (~384px), estreito demais pra um formulário com nome/email/LinkedIn/tipo de acesso/status/bio/tags/cursos/senha, forçando rolagem longa. Campos curtos ficam em grid de 2 colunas (nome+email, tipo de acesso+status, lista de cursos) pra aproveitar a largura extra. Ao adicionar um dialog de edição com muitos campos, considerar alargar em vez de empilhar tudo em uma coluna só.
- **Arquivo `'use server'` só pode exportar função async** — exportar uma constante de dentro de `src/app/actions/*.ts` **passa no `tsc --noEmit` e quebra só no `npm run build`**. Por isso `COMMENT_MAX_LENGTH` mora em `src/lib/comments.ts`, importado tanto pela action quanto pelo componente. Valor compartilhado entre server action e cliente vai sempre num módulo neutro em `src/lib/`.
- **Tarefa de aula: feedback imediato de certo/errado em múltipla escolha/checkboxes (v1.95.0)**. `SubmittedView` (`lesson-task-form.tsx`) compara `option_indices` da resposta contra `correct_options` da questão (já enviado ao membro na query da própria página, `dashboard/aulas/[id]/page.tsx`) e colore cada opção (verde=acertou, vermelho=marcou errado, âmbar="era essa"). Texto livre (`short_text`/`long_text`) **não** tem indicador — não é auto-corrigível, só aparece em Documentos → Notas depois que o admin avalia manualmente. **Bug real corrigido na mesma versão**: a resposta de texto livre não preservava quebra de linha/marcadores ao reabrir a aula — faltava `whitespace-pre-wrap` no `<p>` do `SubmittedView` (o painel do admin e "Notas recebidas" já tinham isso certo, só a visão do próprio aluno na aula estava sem).
- **`/dashboard/aulas/[id]` remonta o componente inteiro a cada troca de aula** — o App Router do Next reconcilia o segmento dinâmico `[id]` como uma montagem nova, não uma atualização de props na instância existente (apesar de `StudyInterface` não ter nenhum `key` explícito). Todo `useState` de `StudyInterface`/filhos parte do zero em cada navegação — é por isso que o reset de `completed`/`showNextBanner` (comentário "Reset só ao TROCAR de aula" no código) só entra em jogo no caso raro de um `revalidatePath` atualizar a MESMA aula sem navegação de verdade; navegação de aula normal já reseta tudo sozinha, de graça. **Bug real corrigido (v1.118.2, chamado CLV-0043): o accordion "Conteúdo do curso" (`study-curriculum.tsx`) fechava o módulo que o aluno estava vendo sempre que ele clicava em "Próxima"/numa aula de outro módulo** — a lista de módulos expandidos vivia só em `useState`, então cada remontagem recalculava do zero via `defaultExpanded()` (que só abre no máximo 1 módulo por vez), substituindo o que estava aberto. Corrigido persistindo o set de módulos expandidos em `localStorage` (chave por `courseId`, mesmo padrão simples de `admin_sidebar_collapsed`) — sobrevive à remontagem porque não depende de o componente continuar vivo. **Achado no processo de corrigir**: a primeira tentativa só persistia dentro do `toggle()` manual e de um `useEffect`, mas nunca gravava o valor calculado no `useState` inicial — então o PRIMEIRO módulo visto (sem nenhum clique manual) nunca ia pro localStorage, e a navegação seguinte "esquecia" dele do mesmo jeito. Corrigido com um único `useEffect` que sincroniza `localStorage` com o `expanded` state sempre que ele muda, cobrindo também o valor inicial. **Ao adicionar estado que precisa sobreviver entre `/dashboard/aulas/[id]`, sempre usar armazenamento fora do React (localStorage/sessionStorage), nunca assumir que `useState` persiste entre aulas.**
- **Navegar entre aulas leva ~3s para a tela trocar**, mesmo com o payload RSC já baixado — é custo de commit da rota, igual no `<Link>` "Próxima" e no avanço automático. Por isso o banner de conclusão faz `router.prefetch()` da próxima aula ao aparecer e mostra "Abrindo..." quando a contagem zera. **Ao testar navegação aqui, usar `waitForURL`, nunca espera fixa**: o avanço automático completo leva ~9s (1s da action + 5s de contagem + ~3s de commit), e uma espera de 8s reporta falha um segundo antes do sucesso — falso negativo que já custou duas "correções" para um bug inexistente.
- **Tarefa de aula: aluno pode refazer até 3 vezes (migração `061`, v1.120.0, chamado CLV-0044)**. `MAX_TASK_ATTEMPTS` mora em `src/lib/lesson-tasks.ts` (não em `lesson-tasks.ts` "use server" — arquivo `'use server'` só pode exportar função async, exportar uma constante de lá passa no `tsc --noEmit` e só quebra no `npm run build`, mesma armadilha já documentada pra `COMMENT_MAX_LENGTH`). **Decisão deliberada: "refazer" reaproveita a MESMA linha de `lesson_task_responses`** (incrementa `attempt_number`, reseta `grade`/`feedback`/`graded_at`, apaga e regrava `lesson_task_answers`) em vez de guardar uma linha por tentativa — sem histórico de tentativas antigas, mas mantém intactas de graça todas as outras telas que já assumiam "uma resposta por aluno por tarefa" sem nenhuma garantia no banco (admin, Notas pendentes/recebidas, KPI "aguardando correção" do Dashboard, Manual Interativo) — nenhuma delas precisou mudar. A migração também formaliza essa invariante com `UNIQUE (task_id, user_id)` (confirmado sem duplicata existente antes de aplicar). `submitTaskResponse` decide sozinho se é a 1ª tentativa (insere) ou um refazer (atualiza) checando se já existe resposta pro par task+user — **um único ponto de entrada**, não uma action separada pra "refazer". Refazer conta como nova submissão pra todo efeito (reabre "aguardando correção" pro admin, dispara `task_submitted` de novo) — intencional, já que uma resposta nova precisa ser corrigida de novo. UI: botão "Refazer teste" só aparece com `attempt_number < 3`; acima disso mostra "Você já usou todas as 3 tentativas". Painel de correção do admin (`task-responses-panel.tsx`) mostra "· tentativa N" quando `attempt_number > 1`, pra não confundir o admin vendo uma nota que ele já tinha dado sumir sozinha.
- **Anotação de aula: salvamento manual + rascunho no servidor (migração `052`)**. `content` = versão salva (é o que Documentos → Anotações lê); `draft_content`/`is_draft` = digitado desde o último Salvar. **Colunas separadas de propósito**: se o rascunho escrevesse em `content`, quem começa a editar uma anotação boa e desiste no meio destruiria o texto original. `saveNoteDraft` **não toca em `updated_at`** — Documentos ordena por essa data e rascunho não pode reordenar a lista — e não chama `revalidatePath` (roda a cada pausa de digitação). Rascunho idêntico ao salvo é descartado, senão digitar-e-desfazer deixaria um falso "não salvo".

Comentário oculto some da lista e da contagem para os demais, mas o autor continua vendo o próprio com aviso. **Ao estender um botão de moderação para `canModerate` na UI, conferir se a action correspondente também aceita colaborador** — foi assim que `deleteComment` (cuja policy de DELETE cobre só autor e admin) passou a falhar em silêncio para o colaborador antes de ser corrigida na mesma versão.

Um insert direto com aninhamento profundo grava, mas a UI não renderiza (`repliesOf` só busca filhos de raiz). Limite de 1000 caracteres validado na action (fonte de verdade) e espelhado no `maxLength`; o contador só aparece nos últimos 200.
- **"Ouvir esta aula" (TTS, `TextToSpeechPlayer` em `study-interface.tsx`, v1.99.0)** usa a Web Speech API (`speechSynthesis`), que **não expõe duração real nem posição exata de reprodução** — só o evento `boundary` (charIndex), com suporte inconsistente entre navegadores. A barra de progresso/tempo é uma ESTIMATIVA: um timer avança a posição com base numa velocidade média de leitura (`CHARS_PER_SECOND_AT_1X = 15`, ajustada pela velocidade escolhida), corrigida quando o `boundary` chega. **Trocar velocidade ou volume no meio da fala exige recriar a `SpeechSynthesisUtterance`** a partir da posição atual (`rate`/`volume` de uma utterance já falando não são alteráveis de forma confiável entre navegadores) — por isso `applyRate`/`applyVolume` cancelam e recriam preservando play/pause; o seek (arrastar a barra) faz o mesmo a partir da posição alvo. Duração total exibida muda com a velocidade escolhida (é `charsRestantes / (15 × rate)`, não um valor fixo).
- **Sugestão real aplicada (v1.122.8, chamado CLV-0050, Cesar): links não são mais lidos em voz alta.** `stripHtml()` (usado só pra montar o texto do TTS, não afeta a renderização visual da aula) agora remove `<a>...</a>` inteiro — tag e conteúdo — ANTES de tirar as demais tags. Motivo: o `autolink` do `RichTextEditor` transforma qualquer URL colada em `<a href="...">` com o texto visível sendo a **própria URL crua**; sem esse filtro, o TTS tentava "pronunciar" a URL letra por letra/barra por barra. Efeito colateral aceito de propósito: um rótulo de link com texto amigável (ex. "clique aqui") também some da narração, não só URLs cruas — bate com o pedido literal do Cesar ("não há necessidade de áudio para links"), sem distinguir os dois casos. Se uma aula tiver conteúdo que é SÓ um link, o texto narrável fica vazio e o player "Ouvir esta aula" nem aparece (mesmo guard `if (!text) return null` que já existia pra aula sem nenhum texto). **Testado sem precisar de áudio real**: aula com conteúdo 100% link → player não renderiza; aula com texto + link → player aparece com duração compatível só com o texto (a URL de ~56 caracteres não entra na conta).
- **CLV-0048 reaberto pelo Cesar ("melhorou bastante, mas não está 100%") — o debounce de 200ms sozinho não bastava, corrigido em v1.124.5.** O debounce por TEMPO não sabe se o dedo/mouse ainda está pressionado — um arraste humano real tem micro-pausas naturais, e qualquer intervalo >200ms entre eventos (mesmo com o ponteiro ainda na tela) já disparava a recriação da fala no MEIO do arraste, exatamente o mesmo sintoma que o debounce deveria ter eliminado ("áudio para enquanto você mexe" + barra "atrasada", cada disparo prematuro reseta a âncora de posição). Confirmado objetivamente: uma pausa sintética de 400ms sem soltar o ponteiro disparava `speak()` de novo mesmo com o debounce em vigor. Corrigido com `seekPointerDownRef`/`volumePointerDownRef` — enquanto o ponteiro está fisicamente pressionado (`onPointerDown` até `onPointerUp`), o timer de debounce **nem chega a ser agendado**; a confirmação de verdade só acontece no `onPointerUp` (`commitSeek`/`commitVolume`, extraídos pra serem chamados tanto pelo debounce quanto pelo release). O debounce continua existindo, mas só entra em jogo quando NÃO há ponteiro envolvido (mudança via teclado num input focado, sem evento de pointer correspondente). **Debounce por tempo sozinho não é a mesma coisa que "esperar o usuário soltar" — um gesto de arraste real não é um fluxo perfeitamente contínuo de eventos, então qualquer lógica que dependa só de "N ms sem novo evento" pode disparar no meio do gesto; quando existe um evento de release de verdade disponível (`pointerup`/`mouseup`/`touchend`), prefira ele como fonte de verdade e use o timer só como fallback pra entradas sem esse conceito (teclado).**
- **Bug real corrigido (v1.122.7, chamado CLV-0048, relatado pelo Cesar): mexer no volume (ou na barra de posição) durante a reprodução deixava a narração "engasgada", como se tivesse ficado muito mais lenta e quase incompreensível.** Causa: `<input type="range">` dispara `onChange` a CADA pixel movido durante o arraste, não só ao soltar — e tanto `applyVolume` quanto `handleSeek` respondiam a cada disparo cancelando (`speechSynthesis.cancel()`) e recriando (`speak()`) a utterance inteira do zero. Um arraste de verdade gera dezenas desses eventos por segundo, então a fala era reiniciada em loop antes de qualquer trecho terminar de tocar — daí soar "lenta": na prática é a MESMA fração inicial sendo repetida sem nunca avançar. Corrigido com debounce de 200ms nos dois (`seekDebounceRef`/`volumeDebounceRef`): o `onChange` só atualiza o estado visual (`setVolume`/`setPlayedChars`, pro slider continuar respondendo ao arraste em tempo real) na hora; o cancel+recreate de verdade só acontece 200ms depois do ÚLTIMO evento, então um arraste inteiro vira uma única recriação, não uma por pixel. Durante um seek "em voo" (aguardando o debounce), o timer de extrapolação da posição é pausado via `isSeekingRef` — senão a barra arrastada "voltava sozinha" por um instante antes do seek de verdade acontecer (a extrapolação continuaria calculando a partir da âncora ANTIGA). Debounces pendentes são cancelados em `handleStop()` e no cleanup de `[html]` — sem isso, um Stop no meio do arraste deixaria o timer disparar depois e reviver a fala sozinha. **Verificado sem depender de áudio real**: instrumentado `speechSynthesis.speak`/`cancel` pra contar chamadas — 21 eventos de "arraste" sintético no volume e no seek resultaram em só 1 recriação cada, confirmando que o debounce colapsa a tempestade de eventos numa única chamada.
- **CLV-0047 reaberto pelo Cesar ("o erro ainda persiste") depois da correção via `boundary` (v1.122.6) — causa raiz diferente, corrigida em v1.124.4.** O evento `onboundary` tem "suporte inconsistente entre navegadores" (já documentado abaixo), mas na prática é pior que isso: em vários Android/Chrome mobile (o aparelho do Cesar, a julgar pelos prints de todos os chamados dele) ele **nunca dispara nenhuma vez**, então a correção anterior nunca tinha dado nenhum sinal pra corrigir a estimativa — o bug original (duração fixa errada a leitura inteira) continuava 100% intacto nesse navegador, apesar do código "corrigido" existir. `onend`, ao contrário do `boundary`, é garantido pela spec (sempre dispara quando a fala termina, com ou sem suporte a `boundary`) — usado agora como calibração terminal: ao final de QUALQUER narração completa, mede a duração REAL (chars da utterance / tempo decorrido de verdade) e grava em `localStorage['tts_observed_chars_per_sec']`. Toda narração SEGUINTE (mesma aula, aula diferente, mesmo depois de recarregar a página) já nasce com a estimativa correta desde o primeiro segundo, sem depender de `boundary` funcionar. `boundary` continua ativo como correção adicional em navegadores que o suportam (não removido, só deixou de ser a ÚNICA fonte de correção).
- **Segundo bug real encontrado testando essa correção**: `observedCharsPerSecRef` era uma **ref**, e `ref.current = X` dentro de um `useEffect` **não dispara re-render** — a duração exibida (calculada no corpo do render) ficava presa no valor antigo até algum OUTRO estado mudar por coincidência (o que só acontecia depois de dar play, quando `setPlayedChars` já causava re-render por outro motivo). Isso mascarava o bug: testado ao vivo (tocando a narração), a duração parecia se corrigir; mas o cenário real do Cesar era abrir a aula e olhar a duração ANTES de tocar — exatamente o caminho que nunca re-renderizava. Corrigido trocando a ref por `useState` (`observedCharsPerSec`) — toda escrita agora naturalmente dispara re-render, incluindo a leitura do valor aprendido no efeito de montagem. **Um valor lido/calculado numa ref, dentro de um efeito que roda só na montagem (sem nenhum `setState` acompanhando), nunca aparece na tela até outro estado mudar por acaso — se o valor precisa refletir no render imediatamente após o efeito, use estado, não ref.**
- **Bug real corrigido (v1.122.6, chamado CLV-0047, relatado pelo Cesar): a duração total mostrada ficava errada a leitura inteira** (ex.: "0:38" pra uma narração real de 46s) porque usava só a constante fixa `CHARS_PER_SECOND_AT_1X = 15`, que é uma média genérica — a voz de verdade do navegador pode ler mais devagar (ou mais rápido). Corrigido com `observedCharsPerSecRef`: cada evento `boundary` já entrega char lido + tempo decorrido de verdade daquela utterance, então dá pra calcular a velocidade REAL observada (normalizada por `atRate`, com guard de `elapsedSec > 1 && charIndex > 30` pra não oscilar com ruído dos primeiros eventos, e clamp `[5, 30]` char/seg contra timing esquisito isolado) e usar esse valor — não mais a constante — tanto no timer de extrapolação quanto no cálculo de `duration`/`current` exibidos. Resultado: a duração mostrada converge pro valor real conforme a fala avança, em vez de ficar errada do início ao fim. Reseta pra constante a cada `html` novo (troca de aula). **Não testável em Chromium headless** (Playwright) da forma que importa — o motor de síntese de voz não tem timing de áudio real nesse ambiente — confirmado apenas que o player renderiza e responde aos controles sem erro; a convergência da estimativa em si só se confirma ouvindo de verdade com cronômetro, mesma classe de limitação já documentada pro Cloudflare Turnstile e pro Web Push.

## Nunca chamar várias Server Actions juntas num `Promise.all` do cliente

Nesta versão do Next.js (16.2.9), quando um client component dispara 2+ Server Actions distintas num só `await Promise.all([...])`: **o servidor executa e persiste TODAS corretamente**, mas a promise no cliente **nunca resolve** — o `await` fica pendurado, o botão gira pra sempre, o toast nunca aparece e o diálogo nunca fecha. Parece que travou (ou que falhou em silêncio, se o usuário recarregar antes de perceber que os dados já foram salvos).

- **Correção**: trocar `Promise.all([a(), b(), c()])` por chamadas sequenciais (`const r1 = await a(); const r2 = await b(); const r3 = await c()`) nos dois diálogos — resolve de forma confiável (confirmado com o navegador realmente recebendo os 3 retornos e a UI atualizando). Como efeito colateral, também consolidamos o `revalidatePath('/admin/membros')` que cada uma das 5 actions envolvidas (`updateMember`, `assignMemberCourses`, `approveMember`, `updateMemberRole`, `assignMemberTags`) chamava por conta própria — removido de dentro delas (só fazem sentido chamadas em sequência a partir desses 2 diálogos, confirmado via grep que não são usadas em nenhum outro lugar) e substituído por um único `router.refresh()` no cliente, depois que toda a sequência terminar. Também corrigido de passagem: `EditMemberDialog` só checava `memberResult?.error` (ignorando erro de tags/cursos); agora checa os 3.
- **Se esse padrão aparecer em outro lugar do projeto**: `grep -rn "Promise.all(\[" src/components` e olhar se o array mistura chamadas a Server Actions importadas de `@/app/actions/*` — se sim, trocar por sequencial. Página/Server Components fazendo `Promise.all` de leituras (`supabase.from(...).select(...)`) não têm esse problema — é específico de **múltiplas Server Actions disparadas juntas por um client component**.
- **Chamada fire-and-forget seguida de `router.refresh()` é cancelada** antes de o servidor terminar (confirmado empiricamente com `syncMemberRdStation`: sem `await`, o evento simplesmente não chegava). Sempre `await` antes de refreshar.
- A investigação completa, com as duas hipóteses plausíveis que se provaram erradas, está em [docs/historico-tecnico.md](docs/historico-tecnico.md#bug-promiseall-de-server-actions-a-investigação).

## RD Station bloqueia envio de e-mail "de marketing" sem base legal (LGPD) — mesmo com fluxo ativo e disparando (v1.113.3)

- **Achado real investigando com o usuário**: um fluxo de automação novo (`universidade-lv-comunicado`) estava **ativo**, com o gatilho certo, disparando corretamente (confirmado por um bloco paralelo de notificação interna que sempre chegava) — mas o bloco "Enviar Email" ficava **permanentemente em 0 entregues** (aba "Interação" do relatório do fluxo na RD Station), sem nenhum erro visível na tela de montar o fluxo. E-mails **transacionais** já existentes (redefinir senha, aprovação/recusa de cadastro, chamado, tarefa corrigida) sempre funcionaram normalmente com a mesma conta/domínio de envio — só esse (um comunicado geral, mais parecido com e-mail de marketing) falhava silenciosamente.
- **Causa**: a RD Station exige uma **base legal (LGPD)** — `legal_bases: [{ category: 'communications', type: 'consent', status: 'granted' }]` no payload do evento de conversão — pra liberar envio de e-mails que ela classifica como marketing/comunicação. Sem isso, o bloco de e-mail do fluxo "roda" (o gatilho é aceito, a automação avança) mas o envio em si é bloqueado, sem aparecer como erro na tela de configuração — só fica visível quando se olha o relatório de entrega de verdade.
- **Corrigido em `src/lib/rdstation.ts`**: `sendConversion()` ganhou um parâmetro opcional `legalBases`, que vira a chave `legal_bases` (array, não string — por isso não cabia no `extra: Record<string, string>` que os outros campos usam) no mesmo nível de `conversion_identifier`/`email` no payload. `rdWelcomeOnRegister` (evento `cadastro`) já manda `MARKETING_CONSENT` — assim todo cadastro novo já nasce com consentimento concedido, sem precisar de ação manual.
- **Backfill pontual pros leads que já existiam antes dessa mudança**: rodado um script avulso (não ficou no código — é operação de uma vez só) mandando um evento de conversão com identificador dedicado `universidade-lv-consentimento-inicial` (sem nenhuma Automação vinculada a ele, só serve pra carregar o `legal_bases`) pra cada usuário real da base (excluídas contas de teste `@example.com`). **Se aparecer um lead novo que nunca passou pelo cadastro normal do app** (ex.: importado manualmente, ou cadastro antigo de antes dessa mudança) **e um e-mail de comunicado não chegar pra ele**, meio caminho andado do diagnóstico é sempre checar consentimento antes de qualquer outra coisa — mesmo com tudo mais parecendo certo no fluxo.
- **Cobertura de TODOS os pontos de criação/edição de conta (v1.113.5)**: `rdWelcomeOnRegister` (cadastro auto-serviço) já mandava `legalBases`, mas existe um **segundo caminho de criação de conta** que não passava por ali — `createMember` (`src/app/actions/members.ts`, admin cria membro/colaborador direto, sem auto-serviço) não disparava nenhum evento de RD Station. Corrigido chamando `rdGrantMarketingConsent(email)` (função nova em `rdstation.ts`, mesmo identificador `consentimento_inicial` do backfill, sem e-mail nenhum associado) logo depois da criação. `syncLeadProfile` (roda sempre que um admin edita um membro, `EditMemberDialog`) também ganhou `legalBases` — cobre o caso de **troca de e-mail**: a RD Station trata e-mail novo como lead novo, então sem isso o e-mail trocado ficaria sem consentimento mesmo o antigo já tendo. **Ao criar um novo caminho de criação de conta no futuro** (ex.: import em massa, integração externa), sempre garantir uma dessas duas chamadas — `rdWelcomeOnRegister` (se fizer sentido mandar o e-mail de boas-vindas) ou só `rdGrantMarketingConsent` (se não).

Aponta pra `/` (rota interna, a landing page do próprio projeto — não é link externo).

- **Os 3 formulários que usavam `<form action={action}>` (padrão `useActionState`) precisaram virar `<form onSubmit={handleSubmit}>`** — o token do captcha só existe depois de uma chamada assíncrona, que precisa rodar ANTES do FormData ser montado; `action={action}` nativo não dá esse gancho. `handleSubmit` monta o FormData manualmente, injeta `captcha_token`, e chama `action(formData)` dentro de `startTransition` (importado de `'react'`, não `useTransition`) — é assim que se invoca manualmente o dispatcher do `useActionState` fora do fluxo nativo de submit, mantendo `pending` funcionando igual. `lead-form.tsx` já usava esse padrão (`onSubmit` + `useTransition` próprio) — só precisou injetar o token no meio.
- **Pré-requisito pro usuário**: criar um site Turnstile em `dash.cloudflare.com/?to=/:account/turnstile` (widget mode **Invisible**, domínio `universidadelv.com.br` + `localhost` pra dev) e preencher `NEXT_PUBLIC_TURNSTILE_SITE_KEY`/`TURNSTILE_SECRET_KEY` no `.env` da VPS (e no `.env.local` de quem for testar localmente).

## E-mail de "redefinir senha" migrado do Supabase pra RD Station (v1.113.0)

- **`forgotPassword` (`src/app/actions/auth.ts`) não chama mais `supabase.auth.resetPasswordForEmail`** (que envia o e-mail nativo do Supabase, direto pelo SMTP deles) — agora usa `adminClient.auth.admin.generateLink({ type: 'recovery', email, options: { redirectTo } })`, que **não envia e-mail nenhum sozinho**, só devolve o link; o envio de verdade é o evento `rdPasswordReset` (`src/lib/rdstation.ts`, mesmo mecanismo dos outros 14 eventos). **Não é preciso desligar nada no painel do Supabase** — o e-mail deles só existia porque o código chamava o método que o dispara; parando de chamar, ele para de sair sozinho.
- **Achado importante testando (não é regressão, é limitação estrutural do PKCE)**: o link gerado por `admin.generateLink` vem no formato de **fragmento** (`#access_token=...&refresh_token=...&type=recovery`), nunca `?code=...` — porque PKCE exige um `code_verifier` guardado no navegador de quem *iniciou* o pedido, e aqui quem inicia é o servidor (service role), sem navegador nenhum por trás. Isso significa que o link **não passa pelo `/auth/callback` (`exchangeCodeForSession`)** como o e-mail nativo do Supabase passava — ele aterrissa direto em `/reset-password` com os tokens no fragmento (que o servidor nunca vê, só o navegador).
- **Corrigido em `reset-password-form.tsx`**: um `useEffect` na montagem lê `window.location.hash`, chama `createClient()` (browser client, `@supabase/ssr`) `.auth.setSession({ access_token, refresh_token })` — isso é o que grava o cookie de sessão que a Server Action `resetPassword` (que roda `supabase.auth.updateUser({ password })`) depende pra funcionar — e só então libera o formulário (estado `sessionState: 'loading' | 'ready' | 'invalid'`, com tela de espera/erro nos dois primeiros casos). Sem isso, a troca de senha falharia em silêncio por falta de sessão no servidor — mesma classe de "RLS/servidor sem sessão" já documentada em outros lugares deste arquivo, só que aqui é ausência total de cookie, não renovação perdida.
- **Efeito colateral confirmado, não é bug**: depois de trocar a senha, `resetPassword` redireciona pra `/login?reset=1`, e como o `setSession` do passo acima já deixou uma sessão válida no navegador, o `proxy.ts` (regra "usuário já autenticado que visita `/login` volta pro painel") pode levar direto pro `/dashboard` sem pedir login de novo — comportamento preexistente do proxy, não alterado por esta mudança.
- **Pré-requisito pro usuário**: criar a Automação `universidade-lv-redefinicao-senha` na RD Station, mesmo processo dos outros 14 eventos (`cf_titulo`/`cf_corpo`/`cf_link`, o link já vem absoluto — é o próprio `action_link` do Supabase, não um caminho relativo do app).
- **`cf_link` vira um link curto (`short_links`, migração `059`), não o `action_link` cru do Supabase (v1.113.2)**: a RD Station **não aceita variável no destino de um link** — o diálogo "Inserir link" do editor só aceita URL literal, e o único jeito que já funcionava nos outros e-mails (chamado, tarefa corrigida) é digitar o link como **texto simples** no corpo, que a RD Station "linkifica" sozinha ao processar a variável. Isso é aceitável quando o link é curto (`/dashboard/feedback?tab=...`), mas o `action_link` de recuperação de senha é um JWT gigante — apareceria por inteiro, feio, no corpo do e-mail. Corrigido gerando um código curto em `short_links` (`code` PK, `target_url`, `expires_at` de 1h) e mandando `https://universidadelv.com.br/r/<code>` pro `cf_link` no lugar; `src/app/r/[code]/route.ts` resolve o código e redireciona pro `target_url` real. Rota pública (`proxy.ts`, `pathname.startsWith('/r/')`) — quem clica ainda não tem sessão nenhuma. Código inexistente/expirado cai em `/forgot-password` em vez de erro. **Sem RLS de leitura** (só `adminClient`, mesmo padrão de `rdstation_tokens`) — não precisa de policy porque nunca é lido pelo client de sessão.
- **Padrão genérico, reaproveitável**: `short_links` não é específico de redefinição de senha — qualquer e-mail futuro da RD Station que precise de um link personalizado (destino diferente por pessoa) pode usar o mesmo mecanismo, sem precisar de tabela nova.

## Ferramentas do repositório (`scripts/`, `.claude/`)

- **`npm run deploy`** (`scripts/deploy-vps.cjs`) — `git pull && npm install && build && pm2 restart` na VPS, com a saída filtrada (imprime tudo se falhar; `-- --verbose` força a saída bruta). Credenciais em `VPS_*` no `.env.local`; requer `npm install -g ssh2`.
- **CAUSA RAIZ do "Apenas admins podem fazer isso" (v1.103.1): campo de senha sempre renderizado + autofill do navegador.** `auth.admin.updateUserById(id, { password })` **revoga TODAS as sessões do usuário** — comprovado isoladamente: logo após a chamada, o `access_token` responde exatamente `Auth session missing!` (status 400) e o `refresh_token` vira `Invalid Refresh Token`. O `EditMemberDialog` mantinha o input "Nova senha" sempre no DOM, e o **gerenciador de senha do navegador autopreenchia** — então TODO salvamento trocava a senha; o admin que editava o próprio perfil se deslogava sozinho e via a mensagem de permissão. Corrigido em duas camadas: (1) o campo só entra no DOM ao clicar em **"Alterar senha"** (sem input, não há o que autopreencher) + `autoComplete="new-password"` + o submit lê o state, não o `FormData`; (2) no servidor, `updateMember` só monta o update de senha se vier string com **≥6 caracteres**. **Ao colocar um `<input type="password">` opcional num formulário, lembrar que o navegador vai preenchê-lo sozinho** — renderizar sob demanda, nunca "sempre visível, deixe em branco para não alterar". Sinal no log: `getUser` falhando com `Auth session missing!` logo depois de um save que mexeu em auth.
- **`getSessionUser()` (`src/lib/session-user.ts`) em vez de `supabase.auth.getUser()` direto nos guards (v1.103.0).** Em algumas requisições de Server Action o client de cookies devolve `AuthSessionMissingError` **mesmo com o cookie de sessão íntegro** — comprovado em produção com diagnóstico temporário: cookie de 2619 bytes, `expires_at` no futuro (`venceu=false`), com `refresh_token` e com o `user` correto, e ainda assim "Auth session missing". Sintoma: admin salvando o próprio perfil recebia **"Apenas admins podem fazer isso"**. `getSessionUser()` tenta o caminho normal e, se ele falhar, lê o `access_token` do cookie e valida com `auth.getUser(token)`. **Não enfraquece a segurança** — essa validação confere assinatura e validade do JWT no próprio Supabase, a mesma checagem do caminho normal; só muda de onde o token foi lido. Verificado: cookie **forjado** (estrutura correta, assinatura inválida) continua sendo bloqueado, os 3 papéis logam normalmente e o logout segue apagando a sessão. **Mensagem "Apenas admins podem fazer isso" é enganosa**: quase sempre significa "a requisição chegou sem credencial", não "seu papel foi recusado" — checar `getSessionUser` antes de suspeitar do `role` no banco.
- **Um diálogo = UMA Server Action (v1.102.7).** `EditMemberDialog` → `saveMemberAll`; `ApproveDialog` (`pending-members.tsx`) → `approveMemberAll`. Antes cada um disparava 4 requisições em sequência (update → tags → cursos → sync RD Station). **Não bastava serem sequenciais**: cada requisição passa pelo middleware, que renova o token quando ele está vencendo, então duas renovações caíam quase juntas (somadas ao heartbeat de presença ao fundo), o `refresh_token` era rotacionado e a retardatária chegava sem sessão. Sintoma para o usuário: parte do formulário salvava e o resto falhava com **"Apenas admins podem fazer isso" mesmo sendo admin** — a mensagem engana, o servidor não rejeitou o cargo, a requisição é que chegou sem credencial. Medido: 4 → 1 requisição por salvamento, nos dois diálogos. **Ao criar diálogo que salva várias coisas, fazer UMA action que orquestra tudo no servidor** — nunca N actions encadeadas no cliente (isso também evita o gotcha do `Promise.all` documentado acima).
- **Renovação de token que falha NÃO pode apagar a sessão (v1.102.6) — causa raiz do "fui deslogado ao salvar".** `createClient()` (`src/lib/supabase/server.ts`) e o `setAll` do `proxy.ts` **ignoram escritas de cookie `sb-*` com valor vazio**. Motivo: o `@supabase/ssr` "apaga a sessão" (escreve cookie vazio) sempre que uma renovação de token falha — inclusive quando falha só porque **outra requisição concorrente já renovou** (o Supabase rotaciona o `refresh_token`, então a retardatária chega com um token já consumido). Numa tela que dispara várias Server Actions em sequência (`EditMemberDialog`) somadas ao heartbeat de presença, isso deslogava o usuário no meio do save. **Evidência que fechou o diagnóstico** (instrumentação temporária no middleware, já removida): o cookie chegava íntegro nas primeiras actions e depois `len=0` — não sumia, era **esvaziado**:
  ```
  POST /admin/membros | user: OK   | cookie[len=2619]
  POST /admin/membros | user: NULL | cookie[len=0]     ← apagado no meio da sequência
  ```
  Ignorar a limpeza é seguro: o cookie anterior segue válido e a próxima requisição renova normal. **Logout de verdade continua funcionando** porque `login()`/`logout()` (`src/app/actions/auth.ts`) — os ÚNICOS pontos server-side com `signOut()` — passam `createClient({ allowSessionClear: true })`. **Ao criar action nova que precise deslogar alguém, lembrar dessa flag**, senão o `signOut()` não terá efeito. Verificado por teste: logout limpa o cookie e `/admin/membros` volta a redirecionar pro login.
- **Prefetch não pode passar pelo middleware (v1.102.3) — a causa raiz do logout no meio do salvamento.** `config.matcher` do `proxy.ts` usa `missing: [{ type: 'header', key: 'next-router-prefetch' }]`. Motivo: o middleware chama `supabase.auth.getUser()`, que **renova o token quando ele está vencendo**; o Next prefetcha todo `<Link>` visível, então dezenas de requisições disparavam a renovação **ao mesmo tempo**, competindo pelo mesmo `refresh_token`. Como o Supabase **rotaciona** esse token, as retardatárias chegavam com um token já consumido → sessão invalidada → o usuário era deslogado no meio de um save e a action respondia "Apenas admins podem fazer isso". **Confirmado que NÃO abre brecha**: prefetch sem sessão devolve só ~234 bytes de metadados de árvore de rota (nenhum dado real — testado grepando por e-mail/nome/código de membro), e a navegação de verdade continua recebendo 307 pro `/login`; os guards de página (`requireAdminPage` etc.) seguem valendo. **Ao investigar "fui deslogado sozinho", suspeite de renovação concorrente de token antes de suspeitar do código de auth.**
- **O middleware NUNCA pode redirecionar uma Server Action (v1.102.2)** — causa raiz do "This page couldn't load" que resistiu a três tentativas de correção. `proxy.ts` agora detecta `request.method === 'POST' && request.headers.has('next-action')` e, nesse caso, **não redireciona** (nem por falta de sessão, nem por papel/inativo): deixa passar e o guard da própria action (`requireAdmin`/`requireCapability`/…) devolve `{ error }`, que vira toast. Um `307` em cima de Server Action faz o cliente do Next receber HTML onde esperava o payload da action, e a aba inteira morre. **Como o bug aparecia**: diálogo que dispara várias actions em sequência (`EditMemberDialog`) + `access_token` perto de expirar → disputa na renovação (a 1ª requisição rotaciona o `refresh_token`, as seguintes chegam com o antigo e sem `user`) → nos logs do nginx, `POST /admin/membros 200` seguido de `POST /admin/membros 307` **no mesmo segundo**, depois `POST /login`. **Por que nunca reproduzia**: conta descartável recém-criada tem token fresco (1h de validade) e nunca renova durante o teste — o bug só afeta sessão antiga, e some em janela anônima (login novo), o que confunde o diagnóstico. **Como reproduzir de propósito**: `context.clearCookies()` no Playwright logo antes de submeter o formulário. **Ao ler logs do nginx procurando isso, o sinal é `200` e `307` em POSTs consecutivos no mesmo segundo** — `499` em rajada é outro sintoma (aborto do cliente), não a causa.
- **Cascata de prefetch em telas admin com lista longa (v1.102.1)**: `/admin/membros` disparava ~46 requisições em 90s. Dois multiplicadores somados: o Next prefetcha **todo `<Link>` visível** (1 por linha da tabela + 12 da sidebar), e o `DashboardAutoRefresh` (`router.refresh()`) **invalida o cache do router e redispara a cascata inteira** a cada ciclo. Nos logs do nginx isso aparece como rajadas seguidas de **`499`** (cliente abortou a conexão — assinatura de aba morrendo/navegando). Corrigido com `prefetch={false}` nos links de linha (cada um renderiza a página de detalhe inteira no servidor, e o usuário clica em no máximo um) + intervalo do auto-refresh de 30s→60s (a janela de presença é 3 min, então continua correto). Resultado medido: 46→20 requisições/90s, prefetch 39→13. **Ao adicionar `<Link>` dentro de lista/tabela em tela com auto-refresh, usar `prefetch={false}`.**
- **Nunca reescrever o e-mail no auth quando ele não mudou** (`updateMember`, `src/app/actions/members.ts`): o código fazia `if (data.email) authUpdate.email = data.email`, sempre verdadeiro, então **todo save** chamava `auth.admin.updateUserById` com o mesmo e-mail. Testado isoladamente e confirmado que **não** revoga a sessão (a hipótese inicial estava errada), mas é uma escrita desnecessária no serviço de auth a cada edição, e pode disparar fluxo de confirmação dependendo da config do projeto. Agora compara com `getUserById` antes e só inclui no update se mudou de fato.
- **`Connection: "upgrade"` fixo no nginx quebrava requisições HTTP normais (corrigido 26/07/2026)** — causa mais provável do "This page couldn't load" intermitente e específico por navegador (relatado no Opera; nunca reproduziu em Chromium/Playwright nem em janela anônima). O `sites-enabled/universidadelv.com.br` tinha `proxy_set_header Connection "upgrade";` **hardcoded**, aplicando o header de upgrade de protocolo a TODA requisição, não só a WebSocket — o upstream (Next) passa a tratar conexões keep-alive normais como tentativa de upgrade, e o resultado varia por navegador/estado de conexão. Corrigido com o padrão canônico: `map $http_upgrade $connection_upgrade` em `/etc/nginx/conf.d/websocket-upgrade.conf` (`default upgrade;` / `'' close;`) + `proxy_set_header Connection $connection_upgrade;`. Confirmado depois: resposta volta com `Connection: keep-alive`. **Cuidado ao fazer backup de config do nginx: NUNCA deixe o `.bak` dentro de `sites-enabled/`** — o include é `sites-enabled/*` (sem filtro de extensão), então o backup vira um segundo `server{}` com o mesmo `server_name` e o nginx avisa `conflicting server name ... ignored`. Backups do projeto ficam em `/root/nginx-backups/`.
- **"This page couldn't load" que NÃO some com Ctrl+F5 = cookie grande demais, não bug de código.** Bug real (26/07/2026): admin com conta antiga não conseguia mais abrir `/admin/membros` — a tela de erro do navegador voltava até com hard refresh. Causa: os cookies de sessão do `@supabase/ssr` são **fragmentados** (`sb-<ref>-auth-token.0`, `.1`, …) e vão todos somados num **único header `Cookie`**; conta com muito tempo de uso acumula chunks até estourar o limite de header, e a requisição morre **antes de chegar na aplicação** (por isso não aparece nada nos logs do PM2, e por isso hard refresh não resolve — o cookie continua sendo enviado). São **duas camadas de limite, as duas precisavam subir**: nginx (`large_client_header_buffers`, padrão `4 8k` → devolvia **HTTP 400**) e Node/Next (`--max-http-header-size`, padrão 16KB → devolvia **HTTP 431**). Corrigido na VPS: `large_client_header_buffers 8 32k` no `http {}` do `/etc/nginx/nginx.conf` (backup em `nginx.conf.bak-<data>`) + `NODE_OPTIONS='--max-http-header-size=32768'` no PM2 (`pm2 restart --update-env` + `pm2 save` pra persistir). **Como diagnosticar de novo em 1 comando** (sem sessão, direto pela borda): `curl -s -o /dev/null -w "%{http_code}" -H "Cookie: junk=$(head -c 16384 /dev/zero | tr '\0' a)" https://universidadelv.com.br/admin/membros` — `307` é saudável; `400`/`431` é o limite estourando. Paliativo pro usuário final: limpar os cookies do site.
- **`pm2 restart` (PM2 em `fork_mode`, 1 instância — confirmado) não é zero-downtime**: janela curta entre o processo antigo morrer e o novo subir. Aba aberta de ANTES do deploy pode falhar ao interagir (`Failed to find Server Action "x"` + `ChunkLoadError` nos logs do PM2) — **essa** falha some com hard refresh, e é o que distingue do caso de cookie acima. A mutação em si já teve sucesso no servidor antes da aba quebrar. Se incomodar com frequência, a solução seria `cluster_mode` com 2+ instâncias (só aí `pm2 reload` é de fato zero-downtime) — mudança de infra, combinar antes.
- **`npm run health-check`** (`scripts/health-check.mjs`, v1.116.0) — verificação diária de saúde da plataforma, pensada para **cron na VPS** (`node scripts/health-check.mjs`), não para rotina agendada do Claude Code — essas expiram sozinhas em 7 dias, incompatível com monitoramento permanente. Roda sem Playwright de propósito (cron de infra não deve carregar Chromium numa VPS de produção): login e RLS dos 3 papéis são testados direto pela API do Supabase (`signInWithPassword` com o client anon + leitura de `profiles` protegida por RLS), conta descartável criada/apagada a cada execução, mesmo padrão do `e2e.mjs`. Verifica também: disponibilidade (`/`, `/login`, `/sitemap.xml`, `/robots.txt` → 200), leituras críticas sem mutação (cursos/feedback/membros — de propósito só leitura, criar chamado/comunicado de teste disparava Notion e notificação real), OAuth da RD Station, API da Notion, e os status pages `status.rdstation.com` (API `/api/v2/status.json`, padrão Statuspage — `maintenance` não conta como falha, só `minor`/`major`/`critical`) e `status.hostgator.com.br` (**não** tem API — não existe endpoint machine-readable documentado; melhor esforço via palavra-chave no banner de texto do topo da página, frágil por natureza: se a HostGator redesenhar a página, o parsing para de funcionar sem avisar). Loga cada execução em `logs/health-check.log` (`.gitignore`, não versionado — cada máquina/VPS acumula o próprio) independente do resultado do alerta, já que o alerta por e-mail é o único canal (decisão do usuário: reaproveitar a RD Station em vez de um segundo serviço tipo ntfy/Slack) — se a própria RD Station estiver fora do ar, o alerta não sai, e o log em disco é a única rede de segurança nesse cenário específico. **Manda e-mail TODO dia, não só em falha (v1.117.1)** — a primeira versão só alertava em falha, e o usuário relatou "não recebi nada hoje" num dia em que estava tudo ok: sem confirmação nenhuma, não dá pra distinguir "está tudo bem" de "o cron parou de rodar sozinho" (o segundo caso, por definição, também não manda e-mail nenhum). `sendReport()` agora dispara sempre o mesmo evento `universidade-lv-alerta-sistema` (RD Station) pro `ADMIN_EMAIL`, mesmo padrão de `admin_cadastro_pendente`/`admin_feedback_novo` — só muda o `cf_titulo`/`cf_corpo` conforme passou ou falhou (✓ resumo vs ⚠ alerta). **Bug real corrigido na mesma versão**: a função de envio referenciava uma constante `ADMIN_EMAIL` solta que tinha sido removida num refactor anterior (sobrou só `env.ADMIN_EMAIL`) — nunca deu erro visível porque toda execução real até então (incluindo o teste manual) tinha passado em todos os 9 checks, e o `--dry-run` retorna antes de tocar nessa variável; só apareceria na primeira falha de verdade em produção, quebrando o envio do alerta bem na hora que mais importa. **Padrão a evitar**: qualquer variável do módulo lida via `env.X` (retorno de `requireEnv`) não pode também existir como constante solta com o mesmo nome — se sobrar uma referência à forma antiga num branch pouco exercitado (aqui, só o caminho de falha real), o teste feliz nunca pega.
- **`@supabase/supabase-js` quebra num script node puro em Node < 22, mesmo sem usar Realtime** — `createClient()` já constrói um `RealtimeClient` internamente, e esse construtor lança exceção síncrona se não achar `WebSocket` nativo no ambiente (só chegou nativo/estável no Node 22; a VPS roda Node 20). O app Next.js nunca esbarra nisso porque o bundler injeta um polyfill; um `node script.mjs` direto, não. Sintoma: `Error: Node.js detected but native WebSocket not found` já na criação do client, antes de qualquer query rodar — só apareceu testando de verdade na VPS (Node 20), não local (Node 24, tem suporte nativo, mascarava o problema). Corrigido com a flag `node --experimental-websocket` (já embutida no script `"health-check"` do `package.json` e no cron) — sem custo em Node ≥ 22, onde a flag é redundante. **Qualquer script `.mjs` novo fora do Next que use `@supabase/supabase-js` e rode na VPS precisa da mesma flag.**
- **`npm run e2e`** (`scripts/e2e.mjs`) — teste com conta descartável: cria o usuário, loga, navega, tira screenshot e **apaga a conta mesmo se falhar**. `-- --role member|collaborator|admin --path dashboard --shot x.png [--clip x,y,w,h] [--keep]`. **Passe `--path` sem barra inicial** — o Git Bash converte `/dashboard` em caminho do Windows.
