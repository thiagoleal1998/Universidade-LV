# Git — Atualização Automática

Após concluir qualquer conjunto de mudanças neste projeto, **sempre** faça commit e push para o repositório remoto:

```
git add <arquivos modificados>
git commit -m "<mensagem descritiva>"
git push origin main
```

- Use mensagens de commit em português, descritivas do que foi feito
- Adicione apenas os arquivos modificados (nunca `git add -A` sem revisar)
- Nunca force-push em `main`
- Sempre faça push ao final de cada tarefa concluída

# Versão do Sistema

A versão fica em `src/lib/version.ts` (constante `APP_VERSION`) e exibida no rodapé do sidebar.

**Regra:** a cada conjunto de mudanças commitado, incremente a versão seguindo semver:
- `patch` (x.x.**N**) — correções de bugs, ajustes visuais, pequenas melhorias
- `minor` (x.**N**.0) — funcionalidades novas ou mudanças relevantes de UX
- `major` (**N**.0.0) — mudanças arquiteturais grandes (raramente)

Atualize `src/lib/version.ts` junto com os demais arquivos no mesmo commit.

## Stack

## Supabase
- `createClient()` — cliente com sessão do usuário (respeita RLS)
- `createAdminClient()` — usa `SUPABASE_SERVICE_ROLE_KEY`, bypassa RLS; use para operações admin
- Projeto ID: definido em `NEXT_PUBLIC_SUPABASE_URL` (ver `.env.local`)
- RLS `profiles`: usuário lê/edita apenas o próprio; admins leem todos (`profiles_select_admin`)
- Notificações: INSERT via `adminClient` (sem política de INSERT — service role bypassa RLS)
- **Relações N→1** (ex.: `tags(name)`, `courses(name)`, `lessons(title)` em joins): o PostgREST retorna **objeto** em runtime, mas o client sem tipos gerados infere **array**. Nunca acesse com `.map()`/`[0]` direto — use `toOne()` de `src/lib/supabase/relations.ts`, que normaliza as duas formas. (Regressão real na v1.50.1: Marketing quebrou com `t.tags.map is not a function` só para usuários com tags.)
- Triggers em `profiles` disparados via auth (GoTrue) rodam com `search_path` restrito — sempre qualifique objetos com `public.` dentro de funções de trigger (ver migração 030).
- **RLS bloqueia joins embutidos para linhas de outro dono, silenciosamente** (sem erro, só vem `null`/vazio): se a query do MEMBRO (client de sessão) faz embed tipo `profiles!fk(full_name)` para um `id` que não é o dele mesmo (ex.: nome do admin responsável por um chamado), a RLS de `profiles` (só lê o próprio perfil) barra o join e o campo volta vazio — mesmo a linha principal sendo do próprio membro. Real em `getMyFeedbackReports` (`src/app/actions/feedback.ts`): resolvido trocando para `adminClient` com filtro explícito `.eq('user_id', user.id)` (a checagem de posse fica no filtro, não na RLS).
- Pacotes `@tiptap/*` precisam ficar todos na MESMA versão exata (ver `package.json`) — as extensões fixam peer dependency `@tiptap/core` na versão exata, não em range; um caret (`^`) num único pacote causa conflito de peer dependency no `npm install` assim que o tiptap publica um patch novo.
- `<Select>` (`src/components/ui/select.tsx`) é baseado em `@base-ui/react/select`, não Radix. **`<SelectValue />` sozinho renderiza o valor bruto**, não o label do `<SelectItem>` selecionado — ele não escaneia os itens renderizados. Precisa de `<SelectValue>{(v) => label[v]}</SelectValue>` (função de mapeamento) ou do prop `items` no `<Select>` raiz. Sem isso, o trigger mostra o `value` cru (ex.: um UUID) em vez do texto — bug real visto no seletor de "Responsável" em `feedback-panel.tsx`.
- **`toast()` (sonner) chamado no primeiro `useEffect` de montagem de uma página pode ser perdido silenciosamente.** O `<Toaster/>` (root layout) só recebe eventos publicados DEPOIS que seu próprio efeito de `ToastState.subscribe()` rodar — e esse subscribe não faz replay de toasts anteriores. Como `{children}` vem antes de `<Toaster/>` no JSX do `src/app/layout.tsx`, um `toast()` disparado no efeito de mount de uma página corre — e às vezes perde — a corrida contra o subscribe do Toaster (mesmo commit, ordem de efeitos por posição na árvore). Sintoma: nenhum erro, o toast simplesmente não aparece, um clique/ação do usuário depois disparando outro toast funciona normal (não é o Toaster que está quebrado, só a chamada síncrona no mount). Correção: empurrar a chamada com `setTimeout(() => toast(...), 0)`. Caso real: toast de "desconectado por inatividade" em `src/components/auth/login-form.tsx` após redirect de `idle-logout-guard.tsx`.

## Papéis e autorização (admin / collaborator / member)
- `profiles.role` aceita `'admin' | 'member' | 'collaborator'` (migração `036`). **Colaborador** = pessoa interna que cria/edita conteúdo apenas da sua área, e estuda como membro comum no `/dashboard` (sem preview de rascunho).
- **Áreas de colaborador** são configuráveis pelo admin (tabela `collaborator_areas`: `name` + `capabilities text[]`), geridas em Admin → Membros → "Áreas de Colaborador" (`collaborator-areas-manager.tsx`). Cada colaborador pertence a UMA área (`profiles.collaborator_area_id`). **Decisão: NÃO reutilizar `tags`** — tags têm semântica de visibilidade de aluno; misturar criaria risco de apagar uma "tag-área" sem perceber que dava poder de escrita.
- **Capacidades** (enum fixo em `src/lib/capabilities.ts`): `courses` (cursos+módulos+aulas), `trainings`, `marketing`, `comercial`, `aereo`, `famtours`, `grupos`. Premiação (TamoJunto Winners), PodViajar e Corrida de Vendas gravam settings globais (`site_settings`, sem `owner_area_id` — não fazem sentido "por posse"), mas são editáveis por quem tem a capacidade `marketing` via `requireCapability('marketing')` + prop `canEdit`. Quando `!canEdit`, mostrar banner âmbar explicando o motivo, não só desabilitar os controles.
- **Cor de tag é hex livre** (`tags.color` aceita `#rrggbb` ou as 10 chaves antigas). Ao renderizar cor de tag em lugar novo, usar `getTagColor()` de `src/lib/tag-colors.ts` e aplicar via `style` inline — **não** `className` (hex arbitrário em runtime não vira classe Tailwind).
- **Dono do conteúdo**: `owner_area_id` (nullable, NULL = global/admin) em `courses`, `training_items`, `marketing_items`, `famtours`, `grupos`, `commercial_conditions`. `modules`/`lessons` herdam via `course_id`. **Reorder global (cursos/módulos/treinamentos) é admin-only** — reordenar um subconjunto bagunçaria os índices; reorder de aulas (escopado ao módulo) exige posse do curso pai.
- **Colaborador VÊ TUDO, só EDITA o que tem capacidade + posse** (v1.71.0 — antes era "só vê o que é seu"). `/admin/cursos` e `/admin/marketing` (as duas únicas telas de conteúdo) mostram TODOS os cursos/treinamentos/itens/famtours/grupos/condições de TODAS as áreas pra qualquer colaborador, inclusive abas sem nenhuma capacidade relacionada (Comercial, Aéreo, Grupos, Corrida de Vendas, Premiação, PodViajar aparecem sempre, em modo leitura). Abrir o detalhe de um curso/módulo/aula de outra área **não bloqueia mais** — abre normal, só os controles de mutação ficam escondidos/desabilitados. Cada tela calcula `canEdit`/`canCreate` (`ctx.role === 'admin' || (ctx.capabilities.includes(cap) && item.owner_area_id === ctx.areaId)`) e repassa como prop pros componentes — **isso é só UX**, a segurança real continua 100% nos guards de mutação (item abaixo), que não mudaram. Padrão de UI pro modo leitura: `<fieldset disabled={!canEdit}>` em volta de formulários inteiros (desabilita inputs/botões nativamente em cascata) + condicionais explícitas pra overlays de upload e pro toolbar do `RichTextEditor` (prop `editable`, não é controle de formulário nativo, fieldset não alcança). Em listas de item (famtours/grupos/etc, fora de um único form), cada botão de Editar/Excluir/Publicar fica atrás de `{item.canEdit && (...)}` explícito — o link de ABRIR o detalhe fica sempre visível (é a porta de entrada pro modo leitura).
- **Camadas de autorização** (`src/lib/authz.ts`): `getAdminContext()` monta `{role, areaId, capabilities}`; guards de action (`requireAdmin`, `requireCapability`, `requireContentAccess`, `requireCourseAccess`→`requireModuleAccess`→`requireLessonAccess` sobem a cadeia de posse) retornam `{error}` — **estes são a segurança real, intocados pela mudança de visibilidade acima**. Guards de página: `requireContentPage()` (novo — só exige admin/collaborator ativo, sem checar capacidade nem posse, usado como entrada em `cursos/page.tsx`/`marketing/page.tsx`) substituiu `requirePageCapability` nesse papel; `requireCoursePage`/`requireModulePage`/`requireLessonPage` agora só confirmam que a entidade existe (404-like), sem bloquear por posse. `requireAdminPage` (admin-only) e `requirePageCapability` (capacidade sem posse) continuam existindo para as demais telas. **As policies RLS continuam admin-only de propósito** — a mutação do colaborador passa pelo guard e usa `adminClient`; se alguma action esquecer o guard/adminClient, a RLS bloqueia silenciosamente (0 linhas, sem erro) — mesmo gotcha da nota de feedback acima.
- **TODA server action de mutação tem guard explícito no topo** (padrão `const ctx = await requireX(); if ('error' in ctx) return { error: ctx.error }`): conteúdo usa capacidade+posse; `members/tags/settings/marketing-settings/announcements/seo/faq` usam `requireAdmin()` (antes não tinham NENHUMA checagem — brecha fechada na v1.63.0). Ao criar action nova, sempre incluir guard — o gate do layout não protege actions.
- Entrada no `/admin`: `proxy.ts` e `admin/layout.tsx` aceitam admin e collaborator ativo. Telas de detalhe buscam dados via `adminClient` APÓS o guard de posse (client de sessão esconderia rascunhos do próprio colaborador).
- `notifyAllMembers` e o `notifyMembers` de training incluem `role IN ('member','collaborator')` — colaboradores também estudam e recebem avisos.
- **Atrás do proxy reverso da VPS, `request.url` / `request.nextUrl.origin` refletem o endereço INTERNO** (`http://localhost:3000/...`), não o domínio público — o nginx não repassa `Host`/`X-Forwarded-*`. Para montar URL absoluta num route handler, usar `process.env.NEXT_PUBLIC_SITE_URL ?? 'https://universidadelv.com.br'`. O `.env.local` precisa de `NEXT_PUBLIC_SITE_URL=http://localhost:3000`, senão o dev local redireciona para produção.
- **Detalhes em [docs/historico-tecnico.md](docs/historico-tecnico.md#papéis-e-autorização-detalhes-e-histórico)**: menu do colaborador item a item, fluxo de cadastro pendente (aprovar/recusar/reconsiderar), modo prévia "ver como colaborador" (`getPreviewAreaContext`, cookie, route handler GET), e os bugs de redirect de feedback já corrigidos.

## Anexos de chamado (foto e documento)

- `feedback_attachments` guarda **os dois casos** (migração `049`): `event_id NULL` = anexo da abertura do chamado; `event_id` preenchido = anexo daquela resposta (`feedback_events`). `mapReports` filtra por isso — sem o filtro, o anexo da resposta apareceria duplicado no topo do chamado.
- **Dois uploads distintos, de propósito**: `uploadFeedbackFile` (só imagem, vira `<img>` inline no editor) e `uploadFeedbackAttachment` (imagem **ou** PDF/Word/Excel/texto, vira anexo listado). O segundo valida contra `ALLOWED_ATTACHMENT_MIME`; `toWebP()` devolve o arquivo intacto quando não é imagem, então dá pra chamar sempre.
- **Render**: imagem continua com thumbnail + `ImageLightbox`; documento usa `AttachmentFileChip` (`src/components/ui/attachment-file-chip.tsx`). Ao montar o índice do lightbox, indexar **só as imagens** — misturar documento na contagem abre a imagem errada.
- `NoteAttachmentPicker` (`src/components/ui/note-attachment-picker.tsx`) é o picker de resposta, compartilhado entre admin e membro (a `addFeedbackNote` é bidirecional). Recebe `idSuffix` porque vários cards ficam abertos ao mesmo tempo e o `<input type="file">` precisa de id único.
- A restrição real de tipo é do **bucket** (`allowed_mime_types`), não só do código — confirmado que rejeita executável, zip e HTML mesmo via service role. Ao liberar um tipo novo, mexer nos dois lugares.
- **Nunca validar anexo só por `file.type`** — o navegador não é confiável. Um `.docx`/`.doc` vindo de Windows sem a associação de tipo registrada chega como `application/octet-stream`, e era rejeitado tanto pela action quanto pelo bucket (bug real da v1.89.1: "não dá pra anexar Word"). `resolveAttachmentMime()` aceita o MIME quando reconhecido e **cai na extensão** quando não; o arquivo é reembrulhado com o tipo resolvido antes de subir, senão `toWebP()` não reconhece imagem e o bucket recusa.
- Como a extensão passou a valer, **a extensão salva vem do MIME resolvido, nunca do nome original** (`extForMime`/`safeFileName`): um `x.exe` enviado com MIME de PDF forjado seria gravado como `.exe` e baixado como executável pelo outro lado do chamado. Vira `x.pdf` no storage e no nome exibido.

## Conteúdo rico gerado por membros (não só admin)
- `RichTextEditor` mora em `src/components/ui/rich-text-editor.tsx` (Tiptap) — usado tanto por admins (`lesson-editor.tsx`, `corrida-vendas-manager.tsx`) quanto por membros (`feedback-ticket-form.tsx`).
- Sempre que HTML gerado por MEMBRO for salvo para ser renderizado depois (`dangerouslySetInnerHTML`) por outro usuário (ex: admin vendo um chamado de feedback), sanitize no server action antes de gravar — usar `isomorphic-dompurify` com allowlist explícita (ver `sanitizeRichText` em `src/app/actions/feedback.ts`). Todo `dangerouslySetInnerHTML` anterior no projeto (anúncios, aulas, corridas) só recebe HTML gerado por admins confiáveis — não sanitizado, e deve continuar assim (não é boundary de confiança). Feedback é o primeiro caso de conteúdo rico membro→admin.

## Notificações
- Tabela `notifications`: `id, user_id, type, title, body, link, read_at, created_at`
- Após inserir notificações: chamar `revalidatePath('/dashboard', 'layout')` para invalidar cache do unread count
- Tipos usados (destinatário entre parênteses): `new_training`/`training_replay`/`training_live_expired` (membros do curso), `announcement` (todos os membros), `lesson_published`/`module_published` (membros com acesso ao curso), `task_submitted` (admins), `task_graded` (membro dono da submissão), `task_opened`/`task_closing_soon`/`task_closing_tomorrow` (membros matriculados, via cron `src/app/api/cron/task-reminders/route.ts`), `community_new_post`/`community_new_reply` (admins), `community_reply` (autor do post), `new_feedback` (admins, ao abrir chamado), `new_member_pending` (admins, cadastro aguardando aprovação), `feedback_update` (membro dono do chamado, quando admin muda status ou responde em `src/app/actions/feedback.ts`).
- **Som/toast em tempo real é escopo limitado, não geral**: nem todo tipo acima toca som — só os que têm um componente cliente dedicado assinando Realtime. Hoje existem dois: `src/components/admin/admin-notification-sound.tsx` (admin, tipos `new_feedback`/`new_member_pending`, montado uma vez em `src/app/(admin)/admin/layout.tsx`) e `src/components/members/feedback-notification-sound.tsx` (membro, só tipo `feedback_update`, montado em `src/app/(members)/dashboard/layout.tsx` **só quando `isTester`**, já que só testador abre chamado). O sino do membro (`notification-bell.tsx`) fora desses tipos é só visual — busca ao clicar, sem realtime/som. Ao adicionar um novo tipo que mereça som, decidir explicitamente se cria/estende um desses componentes; não veio de graça por estar na tabela `notifications`.
- **Realtime + polling (híbrido)**: `notifications` está na publication `supabase_realtime` (migração `033`). **Realtime sozinho não é confiável** (confirmado empiricamente: entrega intermitente do evento `postgres_changes`, mesmo com a tabela corretamente na publication e RLS ok) — por isso os dois componentes acima também fazem polling a cada 15s via `getRecentSoundNotifications` (`src/app/actions/notifications.ts`, genérico — recebe a lista de tipos que interessa a cada chamador) como garantia, deduplicando por `id` num `Set` em ref para não tocar duas vezes se ambas as vias pegarem o mesmo evento. Se precisar de realtime em outra tabela, mesma receita de publication: `ALTER PUBLICATION supabase_realtime ADD TABLE x` (idempotente com `DO $$ ... EXCEPTION WHEN duplicate_object`) — mas considere se vale a pena também ter um fallback de polling.
- **Bug ainda aberto**: `src/app/api/cron/task-reminders/route.ts:69` lê `member_courses.user_id`, mas a coluna real é `member_id` — a query falha em silêncio e não notifica ninguém. Não foi corrigido porque o endpoint parece não estar agendado na VPS; ao mexer nos lembretes de tarefa, corrigir junto.
- **Detalhes em [docs/historico-tecnico.md](docs/historico-tecnico.md#notificações-detalhes-e-histórico)**: deep-link de chamado via `?report=<id>`, prop `redirectFeedbackToAdmin`, e a flakiness de teste que é só compilação do Turbopack.

## Menu do aluno — `member_nav_order` tem 2 cópias e a do lado renderizado NÃO mescla chaves novas sozinha
- **Bug real (v1.69.0), pego ao adicionar "Grupos" ao menu**: existem duas funções `parseMemberNavOrder` diferentes — uma em `settings-form.tsx` (edição pelo admin, já mesclava chaves ausentes com `ALL_MEMBER_NAV_ITEMS`) e outra em `member-sidebar.tsx` (o que **realmente renderiza** o menu do aluno). A segunda só devolvia o array salvo em `settings.member_nav_order` **como está** — se esse JSON já tinha sido salvo antes (e sempre tinha, é o caso normal), um item de menu novo (`grupos`) nunca aparecia, mesmo com tudo mais implementado certo, até o admin abrir e salvar Configurações de novo manualmente.
- Corrigido: `parseMemberNavOrder` em `member-sidebar.tsx` agora mescla chaves ausentes do `DEFAULT` no fim do array salvo (mesma lógica de `settings-form.tsx`). **Ao adicionar um item de menu novo pro aluno, sempre atualizar as 3 coisas** (não são 2 como no menu admin): `MEMBER_NAV_MAP`/`DEFAULT_NAV_LABELS`/array `DEFAULT` de `parseMemberNavOrder` em `member-sidebar.tsx`; `ALL_MEMBER_NAV_ITEMS`/`DEFAULT_MEMBER_NAV_LABELS_FULL` em `settings-form.tsx`; e a prop de visibilidade condicional em `dashboard/layout.tsx` — e **testar de verdade logado como aluno**, não só olhar o código, porque esse bug não aparece em nenhum erro de TypeScript nem de build.

## Upload de imagem de capa (padrão `uploadXCover`) — cuidado com foto de celular
- Padrão usado em `famtours-manager.tsx`/`trainings-manager.tsx` (e potencialmente outros managers com capa): o `<input type="file">` guarda o `File` cru no state; o upload/compressão (`toWebP` em `src/lib/image.ts`, via `sharp`) só acontece **depois**, dentro da server action (`uploadFamtourCover`/`uploadTrainingCover`), chamada como Server Action do Next.js. Isso significa que o **arquivo original (não comprimido)** é quem precisa caber no limite de `experimental.serverActions.bodySizeLimit` (`next.config.ts`, hoje `10mb` — era `5mb`, subido na v1.68.1).
- **Bug real (v1.68.1)**: uma foto de celular direto da câmera (facilmente 5–15MB) estourava esse limite, e como não havia `try/catch` em volta do `await uploadXCover(file)`, o erro do Next.js (corpo grande demais) não virava um toast — quebrava a página inteira (`This page couldn't load`) sem log útil no servidor. Corrigido com duas camadas: (1) guard no `handleFileChange` recusando arquivo `> 8MB` na hora da seleção, com toast explicando; (2) `try/catch` em volta do bloco inteiro do `startTransition` do submit, com toast de fallback genérico. **Ao criar um novo manager com upload de capa, replicar as duas camadas** — não é só copiar o padrão de `cover_url`/preview.

## Convenções
- Server actions ficam em `src/app/actions/`
- Componentes admin em `src/components/admin/`
- Componentes UI reutilizáveis em `src/components/ui/`
- `settings` são pares chave-valor na tabela `site_settings`; tipo e defaults em `src/lib/settings.ts`
- Nav do admin é duplicado em dois lugares que precisam ficar em sincronia: `NAV_ITEMS` em `src/components/admin/admin-sidebar.tsx` (render real, com ícone) e `ALL_NAV_ITEMS` em `src/components/admin/settings-form.tsx` (aba "Menu Admin", reordenável via `nav_order`). Ao adicionar página admin nova, adicionar nos dois + no default de `nav_order` em `src/lib/settings.ts`.
- **Perfil (admin e membro) é a MESMA tela**: `src/app/(admin)/admin/perfil/page.tsx` e `src/app/(members)/dashboard/perfil/page.tsx` renderizam o mesmo `<ProfileTabs>` (`src/components/members/profile-tabs.tsx`), cuja aba "Meu Perfil" usa `ProfileFormCompact` (`src/components/members/profile-form-compact.tsx`) — único lugar a editar para mudar campos de perfil de qualquer um dos dois papéis. Campos hoje: nome, email (read-only), avatar, empresa (`company`), cargo (`job_title`), LinkedIn (`linkedin_url`), salvos via `updateProfile` em `src/app/actions/profile.ts`.
- **Arquivo `'use server'` só pode exportar função async** — exportar uma constante de dentro de `src/app/actions/*.ts` **passa no `tsc --noEmit` e quebra só no `npm run build`**. Por isso `COMMENT_MAX_LENGTH` mora em `src/lib/comments.ts`, importado tanto pela action quanto pelo componente. Valor compartilhado entre server action e cliente vai sempre num módulo neutro em `src/lib/`.
- **Anotação de aula: salvamento manual + rascunho no servidor (migração `052`)**. `content` = versão salva (é o que Documentos → Anotações lê); `draft_content`/`is_draft` = digitado desde o último Salvar. **Colunas separadas de propósito**: se o rascunho escrevesse em `content`, quem começa a editar uma anotação boa e desiste no meio destruiria o texto original. `saveNoteDraft` **não toca em `updated_at`** — Documentos ordena por essa data e rascunho não pode reordenar a lista — e não chama `revalidatePath` (roda a cada pausa de digitação). Rascunho idêntico ao salvo é descartado, senão digitar-e-desfazer deixaria um falso "não salvo".
- **Moderação de comentário de aula (fixar/ocultar, migração `051`)**: quem pode é admin **ou colaborador dono do curso** — guard `requireLessonAccess(lessonId)`, que sobe aula→módulo→curso. `lesson_comments` **não tem policy de UPDATE**, então moderação obriga `adminClient`; pelo client de sessão o update afeta 0 linhas sem erro. Comentário oculto some da lista e da contagem para os demais, mas o autor continua vendo o próprio com aviso. **Ao estender um botão de moderação para `canModerate` na UI, conferir se a action correspondente também aceita colaborador** — foi assim que `deleteComment` (cuja policy de DELETE cobre só autor e admin) passou a falhar em silêncio para o colaborador antes de ser corrigida na mesma versão.
- **Comentários de aula têm respostas de UM nível** (`lesson_comments.parent_id`, migração `050`): responder uma resposta aponta para o comentário raiz dela — a regra vive em `createComment` (que sobe até a raiz e confirma que o pai é da mesma aula), não no banco. Um insert direto com aninhamento profundo grava, mas a UI não renderiza (`repliesOf` só busca filhos de raiz). Limite de 1000 caracteres validado na action (fonte de verdade) e espelhado no `maxLength`; o contador só aparece nos últimos 200.
- **Vídeo do YouTube na área do aluno** usa sempre `StudyVideoPlayer` (`src/components/members/study-video-player.tsx`) + `extractYouTubeId` (`src/lib/youtube.ts`) — nunca um `<iframe>` solto. O player já traz controle de velocidade e o heartbeat que impede o logout por inatividade enquanto o vídeo toca. Usado em aula e no replay de treinamento (`dashboard/treinamentos/[id]`, onde substitui a capa e **não** deve conviver com link "abrir no YouTube" — o objetivo é o aluno não sair da plataforma). ## Nunca chamar várias Server Actions juntas num `Promise.all` do cliente

Nesta versão do Next.js (16.2.9), quando um client component dispara 2+ Server Actions distintas num só `await Promise.all([...])`: **o servidor executa e persiste TODAS corretamente**, mas a promise no cliente **nunca resolve** — o `await` fica pendurado, o botão gira pra sempre, o toast nunca aparece e o diálogo nunca fecha. Parece que travou (ou que falhou em silêncio, se o usuário recarregar antes de perceber que os dados já foram salvos).

- **Correção**: trocar `Promise.all([a(), b(), c()])` por chamadas sequenciais (`const r1 = await a(); const r2 = await b(); const r3 = await c()`) nos dois diálogos — resolve de forma confiável (confirmado com o navegador realmente recebendo os 3 retornos e a UI atualizando). Como efeito colateral, também consolidamos o `revalidatePath('/admin/membros')` que cada uma das 5 actions envolvidas (`updateMember`, `assignMemberCourses`, `approveMember`, `updateMemberRole`, `assignMemberTags`) chamava por conta própria — removido de dentro delas (só fazem sentido chamadas em sequência a partir desses 2 diálogos, confirmado via grep que não são usadas em nenhum outro lugar) e substituído por um único `router.refresh()` no cliente, depois que toda a sequência terminar. Também corrigido de passagem: `EditMemberDialog` só checava `memberResult?.error` (ignorando erro de tags/cursos); agora checa os 3.
- **Se esse padrão aparecer em outro lugar do projeto**: `grep -rn "Promise.all(\[" src/components` e olhar se o array mistura chamadas a Server Actions importadas de `@/app/actions/*` — se sim, trocar por sequencial. Página/Server Components fazendo `Promise.all` de leituras (`supabase.from(...).select(...)`) não têm esse problema — é específico de **múltiplas Server Actions disparadas juntas por um client component**.
- **Chamada fire-and-forget seguida de `router.refresh()` é cancelada** antes de o servidor terminar (confirmado empiricamente com `syncMemberRdStation`: sem `await`, o evento simplesmente não chegava). Sempre `await` antes de refreshar.
- A investigação completa, com as duas hipóteses plausíveis que se provaram erradas, está em [docs/historico-tecnico.md](docs/historico-tecnico.md#bug-promiseall-de-server-actions-a-investigação).

## Ferramentas do repositório (`scripts/`, `.claude/`)
